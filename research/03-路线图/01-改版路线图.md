# Luminous 长期健康伙伴改版路线图

> 日期：2026-08-15
> 服从：`research/01-产品方向/01-大方向结论与改版策略.md` v3
> 口径：`Luminous/plans/` 与 `Lucent/plans/` 中的计划视为上线前必然完成；本路线图不把法律页面等计划项重复列为“尚未完成”，只安排产品价值、真实性和验证工作。

---

## 1. 路线图目标

在招募种子用户前，先让产品能够真实交付以下最小伙伴闭环：

```text
拍照 / 自然语言 / 一键记录 / 授权数据
  → 有覆盖率的个人健康上下文
  → 日、周、月范围理解
  → Today 建议或上下文 AI 回答
  → 用户确认有用、完成、不适用或关闭
  → 后续建议频率与内容发生变化
```

药品与健康事件继续完成各自闭环，但不再作为唯一主链或产品成功指标。

路线图不以功能数量为目标，也不因为某模块已经投入较多就优先。每一项新投入必须说明它如何降低记录负担、提高上下文准确性、产生有用行动或减少打扰。

---

## 2. 固定决策

### 删除

- 综合健康评分及其后端跨维权重。
- Legacy dashboard 中的泛化 AI 周/月报告。
- unknown→0 / unknown→持平的旧趋势投影。
- 静态环境、花粉、UV、假血糖趋势、硬编码置信度和无数据源脚手架。
- 已确认无消费方的死代码与假开关。

### 保留并加强

- 餐食拍照识别、饮水、睡眠、心情、症状、活动、用药等平级输入。
- 自然语言转候选记录。
- Today 建议、证据、反馈、抑制和缓存状态。
- 有覆盖率的日/周/月纵向洞察。
- Assistant 的真实工具、上下文授权、健康记忆、来源展示和提案式写入。
- 药箱、用药提醒、安全 finding、药品说明书和健康事件专题回顾。

### 保留但冻结

- 开放式 GenUI：不删除、不推进、不宣传为现有能力。
- App-side experimental AI runtime seam。
- 桌面/Web 产品化：等待独立用户任务和技术路线研究。

### 保留并分层

- 医疗问答语料不删除。说明书与审校数据优先；DrugBank 按版本和来源展示；开放问答只作低可信教育参考。

### 暂不决策

- 当前五个 Tab 是否增删、重命名或调整 Assistant 层级。
- Next.js Web + Tauri 2 是否成为桌面/Web 最终技术路线。
- 订阅、康复包、CPS 或 B2B 商业模式。

## 3. Phase 0：真实性与统一口径

### 目标

保证后续用户验证测到的是产品价值，而不是假数据、断链、来源不透明或各页面口径冲突。

### 工作项

| 模块 | 动作 | 验收结果 |
|---|---|---|
| Today | 删除静态环境/花粉/UV 与旧 recommendations；修 unknown 饮水问候和页级降级状态 | 未记录不再显示为确定性缺口，任何环境建议都有真实来源和更新时间 |
| Record | 删除假血糖趋势；摘要接真实接口；饮水目标读用户设置 | Record、Today 和详情页对同一事实口径一致 |
| Scan/Search | 识别出口接真实药箱建档；删除硬编码置信度与假桌面临床预览 | 扫描后可以查看来源并完成真实动作 |
| Medicine | 清理 safety-tips、workspace、missed 等死字段；统一 sparse 依从口径 | 用户看到的是已确认/未确认事实，不是虚假依从分 |
| Report | 删除综合评分、泛化 AI 报告和旧 unknown→0 图表 | 不再用一个分数或长文掩盖数据缺口 |
| Assistant | 展示使用的数据源与信任等级；补 AI 边界；开放问答降级标签 | 用户能知道回答用了什么、哪些来源可信度较低 |
| Mine | 删除静态假档案卡和无执行器假开关；档案只收集有消费面的字段 | 不用“完成度”诱导提交无用途敏感数据 |
| Platform | 删除伪造 environment 模块；投递历史只展示真实通道 | 所有横切状态都能回到真实执行记录 |

### 不做

- 不因清理 legacy 报告而删除纵向洞察需求。
- 不删除 GenUI 占位和医疗问答语料。
- 不把现有 Flutter 桌面代码当作需要立即重写的对象。

## 4. Phase 1：最小健康伙伴闭环

### 4.1 低负担输入

1. **餐食**
   - 拍照保存后自动完成低成本视觉识别；
   - 用户查看详情、要求精确营养或候选洞察需要时，再执行菜品分解与 grounding；
   - 输出记录餐次、识别范围、匹配覆盖和用户确认状态。
2. **饮水**
   - Today 与 Record 均可一键追加用户默认容量；
   - 未记录保持 unknown，不用目标减零得出“缺多少”。
3. **睡眠**
   - 保留入睡/醒来快捷合并与手动结构化记录；
   - 平台数据只在设备、地区和授权真实可用时作为增强，不能成为所有用户的前提。
4. **自然语言**
   - 一句话可以生成多个候选记录；
   - 用户确认前不进入正式事实；
   - 保存失败按条目展示并可重试。

### 4.2 个人健康上下文

建立供 Today、纵向洞察和 Assistant 共用的上下文契约：

- 当天事实；
- 最近 7 天和 30 天的单维聚合；
- 每个维度的 observed / partial / unknown 与已记录天数；
- 个人基线和基线所用时间窗口；
- 用户目标、偏好、禁忌和授权；
- 已展示建议、用户反馈、抑制状态和是否观察到后续行为；
- 稳定健康记忆与短期对话记忆分离。

任何派生事实都要能追溯到来源版本，并允许用户查看、纠正或删除。

### 4.3 Today 主动建议

- 生活记录不再按类型永久排除触发；餐食、饮水、睡眠和心情在覆盖率与变化幅度达标时可以进入候选。
- 每天最多突出一条主建议和少量次卡；不能每记一杯水就生成通知。
- 建议固定带时间范围、证据、unknown/partial 说明、一个低风险动作和反馈选项。
- `accepted / later / not_applicable / suppress` 必须真实改变后续频率和排序。
- 医疗和用药安全卡继续由规则、说明书或审校数据裁决，AI 只解释。

### 4.4 纵向洞察

新建与 legacy 报告分离的洞察对象：

- **日**：今天已知什么、哪些维度未知、明天最值得做的一件事。
- **周**：有记录的日期与覆盖率、一个可信模式、一个下周实验。
- **月**：用户选择的维度发生了什么变化、哪些建议被证明有用；不做综合健康评分。
- **事件专题**：保留健康事件四段回顾，作为纵向洞察中的一个专题。

新洞察不生成泛化长文；数据不足时直接说明不足并给低负担补充入口。

### 4.5 上下文 AI

必须用场景而不是工具数量验收：

1. 用户问“我最近为什么总是睡得晚？”助手能引用正确时间范围和有记录天数。
2. 用户问“为什么早上嗓子疼？”助手能同时读取被授权的饮水、睡眠、症状和用药记录，区分事实、可能关联和未知因素，不下病因结论。
3. 用户说“帮我记下今天只喝了两杯水”，助手生成可检查提案，确认后真实写入并刷新 Today。
4. 用户关闭睡眠上下文后，后续回答无法调用睡眠工具，并明确提示授权状态。
5. 用户询问药品时，回答展示说明书 / DrugBank / 开放问答的不同信任等级。

聊天会话管理、重命名、重新生成等继续完善，但优先级低于上下文正确性、健康记忆和来源透明。

## 5. Phase 2：用户价值验证

公开资料只用于形成假设。产品是否成立必须用一手用户行为验证。

### 5.1 问题访谈

围绕六个问题开展访谈：

- 是否愿意用拍照、自然语言、一键操作留下少量数据；
- 饮食、饮水、睡眠中最愿意记录什么；
- 什么建议显得“懂我”，什么建议显得烦；
- 是否会因个人上下文选择 Luminous 而不是普通大模型；
- 没有生病时是否仍有持续价值；
- 是否信任 AI 读取跨日、跨月记录，以及需要什么控制。

先问过去真实行为和放弃原因，再展示原型；不以“你会不会用”这类意向答案直接作结论。

### 5.2 两周日记实验

- 用户自行选择 1–2 个维度，不要求全量打卡；
- 记录每种输入方式的使用次数、耗时与放弃点；
- 每天最多一次建议，每周一次洞察；
- 每次收集有用、不适用、太频繁、执行情况和开放反馈；
- 对同一个问题提供普通大模型基线回答，比较上下文价值。

### 5.3 种子产品验证

只有 Phase 1 的最小伙伴闭环完整后才开始。必须同时观察：

- 每周有用伙伴介入率；
- 非生病周价值率；
- 产生一条有用洞察所需的记录负担；
- 建议打扰率与通知关闭率；
- 上下文引用正确率；
- 用户是否认为“确实结合了我的情况”；
- 各数据源授权的保留与撤销行为。

事件完成率、用药确认率和回顾打开率只作为领域指标。所有数值阈值在获得基线前标为待校准假设，不再预设 15%、25%、50% 等生死线。

## 6. Phase 3：验证后的扩展

只有对应假设得到证据后才启动：

- 自动健康数据同步与厂商适配；
- 更多月度比较和大屏可视化；
- 桌面/Web 的用户任务与 Next.js + Tauri 2 技术路线研究；
- 更多健康领域与家庭协作；
- 收费、订阅、商业合作或 B2B；
- 开放式 GenUI 解冻评审。

医疗问答语料的质量治理可以持续进行，但不以扩大条数作为产品进度。

## 7. 决策门

### 伙伴价值成立

- 用户可以用可接受的输入负担换到有用建议；
- 非生病周仍然产生价值；
- 上下文回答明显优于普通大模型的泛化回答；
- 建议有用率和打扰率达到可继续优化的水平；
- 用户理解并愿意控制跨日/月授权。

### 需要调整

- 某个维度记录负担过高：先改变输入方式或降低所需覆盖率，不直接用通知催打卡。
- 建议重复或烦：减少触达、提高仲裁门槛、学习抑制反馈。
- 上下文回答不可信：暂停扩大场景，优先修时间范围、coverage 和来源引用。
- 用户只在生病时使用：说明日常伙伴假设未成立，重新评估日常场景，不自动退回纯用药工具。

### 停止扩张

- 未完成上下文正确性和隐私控制验证前，不扩展更多健康领域。
- 未证明大屏用户任务前，不启动桌面/Web 重写。
- 未证明用户价值前，不建设支付、CPS 或 B2B 数据故事。

## 8. 验收场景

### 餐食

用户只拍了午餐和晚餐。系统可以说“你今天记录的两餐都以主食为主，蔬菜记录较少”，不能说“你今天碳水超标”。

### 饮水

过去 7 天只有 4 天有足够饮水记录。系统必须显示 4/7 覆盖，不能把另外 3 天当 0 ml。

### 睡眠

过去 7 天有 4 个有记录夜晚在凌晨 2 点后入睡。建议只能基于这 4 天，并给一个可逆的小实验，而不是诊断睡眠障碍。

### 上下文问答

用户问嗓子疼原因。助手引用近期饮水与睡眠事实，同时说明感染、环境等因素未知；出现红旗症状时使用固定规则就医提示。

### 用药

用户新增药物后，风险 finding 必须展示规则或说明书来源；AI 不能自行给风险分、剂量或停药建议。

### 无数据

没有足够记录时，Today 和纵向洞察返回明确空态或补充入口，不生成换皮健康建议。
