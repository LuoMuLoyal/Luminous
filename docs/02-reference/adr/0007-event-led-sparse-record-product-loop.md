# ADR-0007: 事件期优先且允许稀疏记录的产品闭环

- **Status**: superseded
- **Date**: 2026-08-07
- **Superseded**: 2026-08-15 by the long-term health companion direction in [`Product_Vision.md`](../../01-product/Product_Vision.md)
- **Deciders**: LuoMuLoyal

> 本 ADR 保留事件闭环重构的历史决策与已经实施的运行时事实。其"事件为回顾主单位"和"手机端永久唯一核心产品"不再代表当前产品方向：健康事件现为平级专题，日/周/月纵向洞察升为核心；手机端承担当前首发，桌面/Web 等待独立用户任务与技术路线研究。

## Context

Luminous 早期为了比赛展示，逐步形成了通用健康记录、主动建议、7/30 天报告、综合评分、PDF 和医生分享并列的产品形态。这个形态隐含两个未经验证的前提：普通用户会长期完整记录饮水、睡眠和每次服药；用户或医生会主动研究通用健康报告。

现有实现还放大了这一问题：主动建议主要在读取 Today 时生成，基线缺少生产写入，漏服时间和服药槽位口径不可靠，饮水在不同模块分别按次数和容量计算，缺失记录可能被解释为零。继续优化通用报告 UI 不能修复输入成本、分析触发、数据语义和价值交付之间的断裂。

## Decision

Luminous 采用"健康事件期切入、日常轻量维护"的产品闭环，并接受稀疏记录是正常输入：

1. 一次症状、短期用药或换药观察形成有明确起止的健康事件；系统可以提议开始或结束，但必须由用户确认。
2. 产品不得依赖完整手工记录。优先使用提醒计划、计划服药槽位、关键确认和异常补记；缺失表示未知，不表示行为没有发生。
3. `Today` 继续承担主动行动，相关事实变化应触发有界后台重算，而不是等用户打开页面后首次生成。
4. 第五个一级入口保留，但用户任务从 `Report` 改为"回顾"：以健康事件为主单位，展示发生了什么、关键变化、完成情况和下一步。跨维度综合健康评分取消，单维趋势必须显示来源和覆盖率。
5. 就诊摘要、PDF、打印和分享链接移入"回顾 > 更多"，不作为核心使用假设或默认成功指标。
6. 手机端是唯一核心产品。桌面端和完整认证 Web 应用冻结并保留代码，不继续功能对等、发行或产品化；`Luminous-website` 继续承担官网和竞赛展示。
7. 该重构不进入当前 `0.1.0` 联调与发布范围，但不再设为发布门禁。按 `Luminous/plans/2026-08-07-product-loop-program.md` 启动（实施完毕文件已删，2026-08-14 收口）。

## Options Considered

| Option | Pros | Cons |
|--------|------|------|
| 保持通用日常记录 + 周/月报告 | 复用现有 UI 和导出能力，比赛展示完整 | 依赖长期完整记录，报告缺少高频任务，数据不足时价值迅速坍塌 |
| 收缩为纯用药工具 | 边界最清晰，数据主要来自药箱和提醒 | 放弃症状变化、生活记录和事件回顾形成的长期差异化 |
| 事件期优先 + 稀疏记录 + 事件回顾 | 有明确开始、动作和结果；允许不完整输入；保留用药安全优势 | 需要跨前后端合同、触发链、数据口径和 Report UI 的系统性迁移 |

## Consequences

- `0.1.0` 保持当前运行时行为，优先修发布阻断问题；方向文档与运行时之间的差异必须明确标注。
- 产品闭环重构需要先建立健康事件和数据语义合同，再改主动建议、记录交互和回顾体验。
- 既有 Report、桌面端和 Web 代码不会删除，但沉没成本不再决定产品优先级。
- 服药、饮水、睡眠和缺失数据必须在 Today、建议、回顾和导出之间使用同一语义。
- 产品验证从"功能数量、导出次数、记录连续天数"转向事件开始/结束、建议处理、结果确认和回顾使用。
- 产品领域术语以 [`../../01-product/Product_Vision.md`](../../01-product/Product_Vision.md) 为准，实施拆分以 `Luminous/plans/2026-08-07-product-loop-program.md`（实施完毕文件已删，2026-08-14 收口）为准。
