## MVP 范围

MVP 要证明一件事：

> 个人用户愿意在一次有明确起止的健康事件中留下少量关键确认和异常记录，并且会因为 `Today` 上的主动建议卡发生可观察行动，认为这种主动干预比自己临时搜索或手动备忘更有用。

MVP 包含的产品闭环：

- 健康事件的混合式起止：系统可根据新增短期药物、提醒计划或连续症状提出开始/结束建议，但必须由用户确认。
- 症状极简记录：事件开始时记录一次，事件期每天最多主动询问一次“好转 / 差不多 / 加重”；详细症状和严重程度可选。
- 饮水记录保留一键容量追加，但属于可选增强数据；统一以 ml 分析，未记录表示未知。
- 饮食、心情和普通笔记保留自愿记录与回看，暂不进入首阶段主动闭环。
- 睡眠快捷弹窗支持夜间睡眠和午睡的近似时长/质量记录；平台健康数据只能作为可选增强，不能作为普遍可用前提。
- 用药记录按计划服药槽位建模，区分待确认、用户自报已服、跳过和超时未确认；未确认不等同漏服。
- 个人用药盒。
- 用药提醒，包括时间计划、确认已服/漏服和记录漏服事件。
- 新增药物后的安全检查提醒，但只覆盖已有来源可支持的说明书、过敏史、当前用药和已审校规则。
- `Today` 首屏主动建议卡，作为 1.0 的核心产品对象。
- 提案式执行：Assistant 可以生成可执行提案，但任何写操作都必须由用户显式确认后执行。
- 事件期轻量总结和事件结束回顾，前提是用户授权且至少有一个可解释维度。
- 日常维护期可选周回顾，只在单一维度数据覆盖足够时生成，不以完整多维记录为门槛。
- 今日主动建议流，建议必须绑定用户记录、规则或可信来源；不能由模型自由联想出卡。
- “回顾”一级视图：以健康事件为主单位，展示发生了什么、关键变化、完成情况和下一步；时间范围筛选和趋势为次级能力。

合同门控项不应作为已完成 MVP 能力宣传：

- 基于健康事件的真实回顾、单维趋势与结果确认闭环。
- 后端同步的隐私授权、通知偏好和提醒偏好。
- 默认曝光的报告导出/分享动作。
- 药物跨来源匹配、重复成分自动识别、未审校药物相互作用判断。
- 红旗信号规则库、固定安全文案和地图/附近线下支持发现。
- 语音、截图等更重输入形态下的自然语言到结构化记录写入链路。

MVP 不包含：

- 运动恢复。
- 女性健康、经期管理。
- 心理健康正式模块。
- 智能硬件。
- 桌面端继续开发、发行或功能对等；现有代码冻结保留。
- 完整认证 Web 应用的继续扩展。
- 家庭协作。
- 儿童用药。
- 慢病完整管理。
- 皮肤识别、影像识别或其他诊断能力。
- 自动处方、自动调整药量、自动改变服药方案。
- 没有规则、说明书、可信来源或人工审校支撑的药物安全判断。
- AI 自行判断红旗信号、疾病风险分级或就医紧急程度。
- 基于 agent 或地图服务的动态附近就医/药房发现。

心理健康可以作为未来扩展，但第一阶段只允许保留非常轻量的非诊断状态标签，不把它作为核心场景，也不命名为正式心理健康模块。

## 1.0 关键边界

- 主动建议卡的触发源只允许来自：
  - 用户结构化记录
  - 用户明确授权的健康上下文
  - 规则引擎 / 药品数据源命中结果
  - 已存在的提醒计划与执行状态
- 安全类卡必须由规则或已审校数据裁决；AI 只负责解释。
- 趋势 / 行为建议卡允许 AI 做受限归纳，但动作必须低风险、可逆、非诊断。
- 低置信度内容只能作为 `观察项` 进入摘要或回顾，不能进入 `Today` 待办或主卡区域。
- 证据冲突、证据不足或无法落到明确动作时，系统应弃权，不强行出卡。
- 缺失记录一律表示未知，不能直接解释为没有饮水、没有睡眠或没有服药。
- 服药完成度按计划槽位计算；点击“已服”是用户自报确认，不是客观吞服证明。
- 回顾不生成跨维度综合健康评分；趋势必须同时展示数据来源和覆盖情况。
- 冷启动阶段不出强趋势卡；只有规则 / 安全类卡、计划事件卡和保守的记录引导卡可以进入 `Today`。

## 1.0 成功标准

1.0 不以导出次数或分享次数作为主成功指标，而以主动建议是否带来可观察行为改变作为主标准。

建议优先验证：

- 用户是否会处理 `Today` 首屏主卡。
- 用户是否会批准并执行提案式动作。
- 用户是否会因为主动建议去补记录、确认用药、完善档案或调整低风险生活行为。
- 用户是否持续觉得建议“有用而不烦”。
- 用户是否愿意开始并结束一次健康事件。
- 事件结束时，用户是否愿意回答“好转 / 差不多 / 加重”。
