## fix(assistant): 首次无会话时误报加载失败——`/latest` 的 `null` 载荷被当成空响应

现象：账号还没有任何会话时首次进入 AI 对话，页面顶部出现
「AI 对话暂时没有加载出来」告警卡，描述为 `Empty response body (getLatestConversation)`。

链路：`GET /api/v1/user/assistant/latest` 在无会话时按契约返回 **200 + `null`**
（本地探针确认：`content-type: application/json`、`content-length: 4`、body `"null"`）；
`AssistantRemoteDataSource.getLatestConversation()` 用 `_requireData()` 包住 `response.data`，
而 `_requireData()` 的语义是「成功响应体缺失 → network/emptyResponse」，于是合法的
「暂无会话」状态必然被判成失败。仓储层本来就写了 `if (dto == null) return null;`
（`AssistantConversation?` 契约），只是数据源没让 `null` 通过。

修复：`getLatestConversation()` 直接返回 `response.data`，`null` 原样上抛；其余仍要求
非空载荷的端点保持 `_requireData()` 不变。

测试：`test/assistant/remote_data_source_test.dart` 新增
「getLatestConversation returns null when no conversation exists」（200 + `null` 载荷 → `null`，
而非 failure），与既有的 `getCapabilities` 空响应用例并存。

## fix(network): SSE 请求被 Web XHR 的 10s 总超时掐断

现象：Web 端助手回答耗时较长时以「这次回复没有完成 / 连接中断了」结束。

原因：dio 的 Web 适配器只有一个超时旋钮——`xhr.timeout = connectTimeout + receiveTimeout`
（`dio_web_adapter` `adapter_impl.dart`）。`LucentSseClient._postAndDecode` 只把
`receiveTimeout` 置 0（意图「不限超时」），`connectTimeout` 仍继承 `BaseOptions` 的 10s，
在 Web 上退化为「整条流 10s 总期限」：超过 10s 的回答被 `xhr.abort()` →
`receiveTimeout`/`connectionError`，`classifySendError` 判为 `streamInterrupted`。

修复：SSE 请求同时把 `connectTimeout` 置 `Duration.zero`（dio 中 0 即不设超时；IO 适配器
`> Duration.zero` 才生效，故原生端一并取消 SSE 的连接超时），并在注释里记录 Web 适配器
会把两个超时相加这一约束。

测试：`test/core/network/sse_test.dart` 新增
「leaves the SSE request without a connection or receive deadline」——断言请求实际下发时
connect/receive 均为 0（修复前前者继承 10s，用例失败）。

验证：`flutter analyze` 零 issue；`flutter test test/assistant test/core/network` 全绿。

遗留：Web 端 `ResponseType.stream` 目前不真正流式（dio Web 适配器用 XHR + arraybuffer，
整流 body 到齐才交给解析器），回答在 Web 上是「一次性出现」；恢复 Web 逐字流式需要
fetch + ReadableStream 适配器或 EventSource 方案，已登记 `docs/TODO.md`。

## fix(auth): 会话恢复的显式刷新与拦截器 401 自动刷新抢用同一个一次性 refresh token

现象：中午登录、晚上仍有效的会话被判为「无法刷新」，用户被强制登出。后端日志可见同一秒内
两次 `POST /api/v1/auth/refresh`，一次轮换成功后紧接着 `Refresh token invalid` 401；
前端 `AuthSessionNotifier.restore` 因此拿到 `AUTH_REFRESH_TOKEN_INVALID` 并清空 session store，
随后的 `GET /user/health-context` 以 `AUTH_REQUIRED`（无 Authorization 头）失败。

根因：Lucent 的 refresh token 是**一次性**的——`AuthSessionRepository.claimSessionForRefresh()`
用原子 `deleteMany` 抢占 `UserSession` 行，第二个使用者必然 401。而客户端有两条互不知情的刷新路径
并存：
1. `AuthInterceptor` 的 401 自动刷新（`_refreshTokens()` 只在本拦截器实例内合并并发调用）；
2. `LucentAuthRepository.refreshSession()` 直接打生成客户端的 `auth.refreshSession()`，
   不经过任何合并。

`SessionProvider._doRestore()` 先 `fetchAccount()`（401 触发路径 1），失败后再走路径 2。
两条路径交错时，后到者拿到 `AUTH_REFRESH_TOKEN_INVALID`，401 分支随即 `_clearSessionAndNotify()`，
把用户仍然健康的会话清掉——正是日志里的表现。

修复：刷新入口唯一化。
- `AuthInterceptor` 新增公开 `refreshSession()`，复用同一个 `_refreshFuture` 合并槽；`_refreshTokens()`
  改为 `async` 包装（`async` 体在首个 `await` 前同步执行，确保合并槽在任何调用者观察到之前已赋值）。
  新增 `_RefreshUnavailable` 结果类型，让「本地已无 refresh token」不再以 `null` 表达。
  刷新失败时重抛 `_lastRefreshError`（真实状态码 + Problem Details body），交给调用方错误映射。
- `LucentDioClient.refreshSession()` 暴露该入口；`authRepositoryProvider` 把它注入
  `LucentAuthRepository`，会话恢复的显式刷新因此与拦截器共享同一次在途刷新。
- `AuthSession.expiresInSeconds` 由常量 `kDefaultAccessTokenTtlSeconds` 填充：刷新端点返回的
  `expiresIn` 不再被拦截器保留，访问令牌有效期由 JWT `exp` 决定，该字段仅作展示语义。

测试：`test/core/network/interceptors/auth_interceptor_test.dart` 新增
「an explicit refresh concurrent with the 401 refresh spends the single-use refresh token only once」——
用 `_SingleUseRefreshAdapter`（模拟一次性轮换语义，记录每次被提交的 token）在拦截器刷新在途时发起
显式刷新，断言提交序列恰为 `['rt-1']`。修复前该用例记录到 `['rt-1','rt-2']`（重复消费）。
`test/auth/remote_data_source_failure_test.dart` 改为经真实 `LucentDioClient` 刷新路径取证，
错误码映射覆盖不变。

验证：`flutter analyze` 零 issue；`flutter test` 全绿。

## fix(network): 会话 token 落盘原子化，消除「新 access + 旧 refresh」撕裂窗口

现象（与上一条同源的次要隐患）：`LucentSessionStore.write()` 分两次写入 access token 与
refresh token。两次写入之间到达的请求会读到「新 access token + 上一个 refresh token」，
于是把**已被服务端消费过**的 refresh token 再次提交给 `/auth/refresh`；Lucent 的 refresh token
是一次性的（`claimSessionForRefresh` 原子抢占），该请求必然 401，401 分支随即清会话。

修复：两套实现都改成单键 JSON 载荷原子写入——`{accessToken, refreshToken}` 编成一条
`jsonEncode`，一次 `setString` / 一次 `storage.write` 落盘，读者再也观察不到半更新状态。
- `SharedPrefsLucentSessionStore`：载荷写在 `lucent_access_token`（沿用旧键名，按前导 `{`
  区分新旧格式），旧键 `lucent_refresh_token` 仅作兼容读取。
- `SecureLucentSessionStore`：同理写入单键载荷；`flutter_secure_storage` 10.x 无 `writeAll`，
  单键写入是唯一不产生撕裂窗口的形态。
- 迁移：`read()` 命中旧双键布局时，先把整对重新编码进载荷键，**再**删除旧 refresh 键；
  顺序不可颠倒——裸 access token 就存在载荷键下，先删后写会丢掉半对。

## fix(auth): 密码登录成功后停在登录页——`goAfterLogin` 漏传 `fallbackHome`

现象：密码登录请求成功（后端有请求日志）、会话也已变为已登录，但路由仍停在 `/login`；手动退回落到
`/` 才看到已登录态。

根因：`login.dart` 的提交回调在成功后调 `goAfterLogin(context, returnTo: returnTo)`，而
`goAfterLogin` 仅在 `returnTo` 可解析时跳转；`returnTo` 为空时是否回退 `Routes.home` 取决于
`fallbackHome`（默认 `false`），于是缺 `return-to` 时该调用是**静默空操作**。OAuth 的各调用点
（`oauth_handlers.dart`、`oauth_callback_hook.dart`）都传了 `fallbackHome: true`，只有密码/验证码
登录这一处漏传。

触发入口：退出登录（`features/settings/presentation/pages/page.dart`、
`features/auth/presentation/pages/account_manage_sections.dart|account_settings.dart|sessions.dart`、
`features/mine/presentation/widgets/sections/account_security.dart`）与「去登录」链接
（`register.dart`、`forgot_password.dart`）都跳到**裸 `/login`**（不带 `return-to`），即命中该空操作。

修复：该调用点补 `fallbackHome: true`，与其余调用点一致。登录后跳转因此不再依赖 `app/router.dart`
守卫的 `refresh()` 重定向这条侧信道——它平时掩盖了本缺陷（实测守卫链路本身是通的：会话变更 →
`bootstrap.dart` 的 listener → `refresh()` → `/login` 变 `/`），但它受会话通知时序影响，不能作为
登录后跳转的唯一依据。

非回归说明：该行自 `bff0b5b2`（2026-07-12）起即未传该参数，`b8177527`（2026-09-07 OAuth 拆分）只是
原样搬移，故属长期隐患而非近期任务引入。

验证：`test/auth/login_page_test.dart` 新增「Login page leaves the login route after password login
without returnTo」——修复前断言失败（`LoginPage` 仍在），修复后通过；`flutter test test/auth` 与
`test/app` 全绿；`flutter analyze` 零 issue。测试盲区一并记录：原有登录用例只覆盖带 `return-to`
与「仅断言会话状态」两种，且 `test/app/router_test.dart` 用
`_testRouter.configuration.routes` 重建裸 `GoRouter`，**丢掉了 redirect**，守卫从未被测试覆盖。

文档同步：`lib/features/auth/README.md`（陷阱与决策：登录后跳转不变量）。

遗留观察（未取证）：未能从代码复现「守卫重定向也没兜住」的原因。若症状复现，下一个嫌疑是
`AuthSessionNotifier.build` 的 `client.onSessionExpired`——`!isLoading` 时任意不可恢复 401 会清空 UI
会话，而登录成功后 `healthContextSnapshotProvider` 失效触发的受保护请求正好落在该窗口；需加日志取证。
