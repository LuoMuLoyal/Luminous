## refactor(arch): 引入 arch_guard 做循环依赖检查

### 为什么

`--clean-layers`（R1–R9）管的是层间 import **方向**，但没有任何规则能发现**循环依赖**。
仓库里积了 7 组环，其中一组 259 个文件（hub 是 `lib/app/router.dart`），靠人眼和 review
发现不了。

### 落地

- 依赖：`arch_guard: ^1.10.0`（dev_dependencies）。
- 配置 `arch_guard.yaml`：分层是 `luminous_lints --clean-layers` 的粗粒度镜像，**不是
  第二套门禁**。文件属于第一个命中的层，所以 `app_seam` / `entry` 排在 `app` 前面。
- 冻结清单 `arch_guard_baseline.json`：存量问题只冻结、不阻断；`dart run arch_guard
  --update-baseline` 在真正修掉一组后收窄。
- 本地脚本 `scripts/arch/guard.dart`：只把「新增循环依赖」和「有文件没归层」当阻断项。
  层违规仍归 `--clean-layers`——两套规则同时阻断会让人重复处理同一个问题。

### 结果

循环组数从 7 降到 2，两组剩余作为已知债务记在 `docs/TODO.md`：
259 文件主环、`database.dart` ↔ `daos/**`（drift 生成物约束，实测 5 种拆法都绕不开
"DAO 要 `AppDatabase`" 与 "`database.dart` 要列全 DAO" 的互为充要条件）。

### 修掉的环

- `core/design`：`SemanticColors` 与调色板解析互相 import → 把 `FColors.semantic`
  访问器移进 `semantic_color.dart`。
- `core/i18n`：`app_locale.dart` 反向 `export localeControllerProvider` → 去掉该
  export，12 个调用点改为显式 import `core/i18n/locale.dart`。
- `l10n`：`gen-l10n` 生成物自环 → `arch_guard.yaml` 排除该目录（AOT 编译时整组合进
  一个库，运行时无害，且不得手改）。
- `app/composition` 两组：`health_sync` 装配 ↔ 数据层 provider、`review` ↔ `tokens`
  → 把数据层 provider 挪进装配文件，反向改为纯 `export`。
- `core → app/router`：`Routes` 常量表下沉到 `lib/core/router/app_routes.dart`，
  `lib/app/router.dart` 保留 re-export，既有 `Routes.*` 调用点不变。

### 验证

`dart run scripts/arch/guard.dart` → 2 组已知、0 新增；`flutter analyze` 干净；
`test/core/database`、`test/health_data`、`test/app`、`test/core/router` 全绿。

## feat(lints): 新增 no_throw 规则，错误统一走失败通道

### 规则

`tool/luminous_lints/lib/src/no_throw.dart`：

- `application/`、`presentation/` 禁止 `throw`；`data/` 只许抛 failure 值；
  `domain/`、`lib/core/`、`lib/app/`、测试不扫描（domain 的 `FormatException` 留在
  `fromJson` 工厂里，由 data 边界映射）。
- 放行：`LucentFailure(...)`、`LucentFailureException(...)`、`throw failure`、
  `mapSseStreamError(...)` 等 `…failure…` 构造调用、以及 `XException` 形式的具名领域守卫。
- 宿主契约豁免：闭包作为实参传给包 API、`@override` 的方法。

### 配套

`lib/core/providers/channel.dart`：`unwrapFailure(...)`（`Left` → `LucentFailureException`）、
`timeoutFailure(...)`、`LucentFailureException`。`LucentErrorMapper.fromObject` 加 unwrap
分支，失败对象在 Future 通道里换了包装但保持同一身份。

### 迁移

命中从 32 处降到个位数。改动主要集中在：
`health_event` 协议不变量、`medicine` 两个数据源、`record` 删除协议检查、
`scan` 的 OCR 失败（新增 domain 词表 `OcrFailure`）、`review` 三个 provider 与 dashboard、
`record` dashboard、`health_event` 写操作（收口到 `_mutate`）、`i18n` 的 locale 控制器。

`LucentFailureException` 只实现 `Exception`，不是 `Error`：`AsyncValue.error` 与
`catch (e)` 照常工作，但 riverpod 的重试策略需要显式关闭才看得到错误态（测试里已经
按这个口径处理）。

### 验证

`flutter analyze` 干净；`test/review`、`test/health_event`、`test/scan`、`test/medicine`、
`test/record` 全绿。

## test(review): 修组件化之后遗留的红

### 根因

6 条渲染态用例 + 1 条 `page_test` 用例从 `f6f0a3da8`（review 主路径改
`ComponentHost` + descriptor）之后就一直红，与本次改造无关（在 `a0245d829` 的
worktree 上逐条复现过）。三个独立原因：

1. 测试只 `pump()` 一次，事件历史 / 看板是异步 provider，第二帧才落树。
2. `AsyncValue.when` 的判定顺序把 `AsyncError` 当成 loading（riverpod 3 重试期间
   `isLoading` 为真），错误态用例永远停在骨架 → 关掉 `ProviderContainer` 的重试。
3. 断言打在了组件化时被合并的旧形态上：`review-no-event-card` 在「数据过稀」时按
   README 不变量就该让位给记录引导卡；`error-with-cache` 的事件区 helper
   `_currentReview` 在 `hasError` 时一律返回 null，刷新失败期间不重绘是既有契约。

### 处理

不放宽断言，改成对准组件化后的真实行为：补第二帧、关重试、断言换成
「横幅出现 + 页面没退化成错误态/骨架 + 记录引导卡让位」。

### 验证

`flutter test test/review` 全绿（325 条）。

## refactor(composition): 组件值类型下沉，分层违规清零

### 根因

`component id` / `size` / `surface` / `layout` 这些**纯值类型**原先和渲染宿主一起放在
`lib/core/composition/`。customizer 的 `domain/` 要用它们（编排草稿以 surface 与组件
id 为维度），但 `domain/` 不允许 import `lib/core/**`，于是整个 feature 被迫违规：

- `domain_purity` 4 条、`data_layer` 4 条、`application_layer` 7 条，全部来自同一批
  import。

### 处理

- 值类型下沉到 `lib/shared/domain/composition/`（`shared/domain/` 是门禁认可的共享
  内核，纯 Dart、无框架依赖）：`id.dart`、`size.dart`、`layout.dart`、`surface.dart`
  （`SurfaceId` / `SurfaceDefinition` / `SurfaceCatalog`）。
- `lib/core/composition/` 只留渲染与装配：`descriptor` / `host` / `registry` /
  `responsive` 与 `surface.dart` 里那几个 Riverpod provider。
- **不做 re-export 转发**：re-export 只是把改动量推给下一个人，domain 仍然依赖 core。
  所有调用点改为直接 import `shared/domain/composition/*`。
- `layoutRepositoryProvider` 从 `customizer/application/layout_store.dart` 移到
  `lib/app/composition/customizer/layout_repository.dart`：装配要同时看见 `data/` 实现
  与 `core/storage`，而 `application/` 两样都不允许 import。
- `layout_store.dart` 本身是 presentation 的读模型（它读 `surfaceCatalogProvider`，
  属于 `app/composition` 白名单），移到 `customizer/presentation/providers/`。

### 结果

`--clean-layers` 从 41 条降到 26 条，**`application_layer` / `domain_purity` /
`data_layer` 三类清零**。剩余只有 24 条 `cross_feature_import`（既有 providers 接缝，
按 AGENTS.md 是 sanctioned 形态）与 2 条 `directory_file_cap`。

### 验证

`flutter analyze` 全仓干净；`test/customizer`、`test/core/composition`、
`test/today`、`test/record`、`test/review` 全绿。
