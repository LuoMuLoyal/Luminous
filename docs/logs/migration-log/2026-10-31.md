## refactor(arch): 引入 arch_guard 做循环依赖检查

### 为什么

`--clean-layers`（R1–R9）管的是层间 import **方向**，但没有任何规则能发现**循环依赖**。
仓库里积了 7 组环，其中一组 259 个文件（hub 是 `lib/app/router.dart`），靠人眼和 review
发现不了。

### 落地

- 依赖：`arch_guard: ^1.10.0`（dev_dependencies）。
- 配置 `arch_guard.yaml`：分层是 `luminous_lints --clean-layers` 的粗粒度镜像，**不是
  第二套门禁**。文件属于第一个命中的层，所以 `app_seam` / `entry` 排在 `app` 前面。
- 冻结清单 `arch_guard_baseline.json`：存量问题只冻结、不阻断；`dart run arch_guard
  --update-baseline` 在真正修掉一组后收窄。
- 本地脚本 `scripts/arch/guard.dart`：只把「新增循环依赖」和「有文件没归层」当阻断项。
  层违规仍归 `--clean-layers`——两套规则同时阻断会让人重复处理同一个问题。

### 结果

循环组数从 7 降到 2，两组剩余作为已知债务记在 `docs/TODO.md`：
259 文件主环、`database.dart` ↔ `daos/**`（drift 生成物约束，实测 5 种拆法都绕不开
"DAO 要 `AppDatabase`" 与 "`database.dart` 要列全 DAO" 的互为充要条件）。

### 修掉的环

- `core/design`：`SemanticColors` 与调色板解析互相 import → 把 `FColors.semantic`
  访问器移进 `semantic_color.dart`。
- `core/i18n`：`app_locale.dart` 反向 `export localeControllerProvider` → 去掉该
  export，12 个调用点改为显式 import `core/i18n/locale.dart`。
- `l10n`：`gen-l10n` 生成物自环 → `arch_guard.yaml` 排除该目录（AOT 编译时整组合进
  一个库，运行时无害，且不得手改）。
- `app/composition` 两组：`health_sync` 装配 ↔ 数据层 provider、`review` ↔ `tokens`
  → 把数据层 provider 挪进装配文件，反向改为纯 `export`。
- `core → app/router`：`Routes` 常量表下沉到 `lib/core/router/app_routes.dart`，
  `lib/app/router.dart` 保留 re-export，既有 `Routes.*` 调用点不变。

### 验证

`dart run scripts/arch/guard.dart` → 2 组已知、0 新增；`flutter analyze` 干净；
`test/core/database`、`test/health_data`、`test/app`、`test/core/router` 全绿。

## feat(lints): 新增 no_throw 规则，错误统一走失败通道

### 规则

`tool/luminous_lints/lib/src/no_throw.dart`：

- `application/`、`presentation/` 禁止 `throw`；`data/` 只许抛 failure 值；
  `domain/`、`lib/core/`、`lib/app/`、测试不扫描（domain 的 `FormatException` 留在
  `fromJson` 工厂里，由 data 边界映射）。
- 放行：`LucentFailure(...)`、`LucentFailureException(...)`、`throw failure`、
  `mapSseStreamError(...)` 等 `…failure…` 构造调用、以及 `XException` 形式的具名领域守卫。
- 宿主契约豁免：闭包作为实参传给包 API、`@override` 的方法。

### 配套

`lib/core/providers/channel.dart`：`unwrapFailure(...)`（`Left` → `LucentFailureException`）、
`timeoutFailure(...)`、`LucentFailureException`。`LucentErrorMapper.fromObject` 加 unwrap
分支，失败对象在 Future 通道里换了包装但保持同一身份。

### 迁移

命中从 32 处降到个位数。改动主要集中在：
`health_event` 协议不变量、`medicine` 两个数据源、`record` 删除协议检查、
`scan` 的 OCR 失败（新增 domain 词表 `OcrFailure`）、`review` 三个 provider 与 dashboard、
`record` dashboard、`health_event` 写操作（收口到 `_mutate`）、`i18n` 的 locale 控制器。

`LucentFailureException` 只实现 `Exception`，不是 `Error`：`AsyncValue.error` 与
`catch (e)` 照常工作，但 riverpod 的重试策略需要显式关闭才看得到错误态（测试里已经
按这个口径处理）。

### 验证

`flutter analyze` 干净；`test/review`、`test/health_event`、`test/scan`、`test/medicine`、
`test/record` 全绿。

## test(review): 修组件化之后遗留的红

### 根因

6 条渲染态用例 + 1 条 `page_test` 用例从 `f6f0a3da8`（review 主路径改
`ComponentHost` + descriptor）之后就一直红，与本次改造无关（在 `a0245d829` 的
worktree 上逐条复现过）。三个独立原因：

1. 测试只 `pump()` 一次，事件历史 / 看板是异步 provider，第二帧才落树。
2. `AsyncValue.when` 的判定顺序把 `AsyncError` 当成 loading（riverpod 3 重试期间
   `isLoading` 为真），错误态用例永远停在骨架 → 关掉 `ProviderContainer` 的重试。
3. 断言打在了组件化时被合并的旧形态上：`review-no-event-card` 在「数据过稀」时按
   README 不变量就该让位给记录引导卡；`error-with-cache` 的事件区 helper
   `_currentReview` 在 `hasError` 时一律返回 null，刷新失败期间不重绘是既有契约。

### 处理

不放宽断言，改成对准组件化后的真实行为：补第二帧、关重试、断言换成
「横幅出现 + 页面没退化成错误态/骨架 + 记录引导卡让位」。

### 验证

`flutter test test/review` 全绿（325 条）。

## refactor(composition): 组件值类型下沉，分层违规清零

### 根因

`component id` / `size` / `surface` / `layout` 这些**纯值类型**原先和渲染宿主一起放在
`lib/core/composition/`。customizer 的 `domain/` 要用它们（编排草稿以 surface 与组件
id 为维度），但 `domain/` 不允许 import `lib/core/**`，于是整个 feature 被迫违规：

- `domain_purity` 4 条、`data_layer` 4 条、`application_layer` 7 条，全部来自同一批
  import。

### 处理

- 值类型下沉到 `lib/shared/domain/composition/`（`shared/domain/` 是门禁认可的共享
  内核，纯 Dart、无框架依赖）：`id.dart`、`size.dart`、`layout.dart`、`surface.dart`
  （`SurfaceId` / `SurfaceDefinition` / `SurfaceCatalog`）。
- `lib/core/composition/` 只留渲染与装配：`descriptor` / `host` / `registry` /
  `responsive` 与 `surface.dart` 里那几个 Riverpod provider。
- **不做 re-export 转发**：re-export 只是把改动量推给下一个人，domain 仍然依赖 core。
  所有调用点改为直接 import `shared/domain/composition/*`。
- `layoutRepositoryProvider` 从 `customizer/application/layout_store.dart` 移到
  `lib/app/composition/customizer/layout_repository.dart`：装配要同时看见 `data/` 实现
  与 `core/storage`，而 `application/` 两样都不允许 import。
- `layout_store.dart` 本身是 presentation 的读模型（它读 `surfaceCatalogProvider`，
  属于 `app/composition` 白名单），移到 `customizer/presentation/providers/`。

### 结果

`--clean-layers` 从 41 条降到 26 条，**`application_layer` / `domain_purity` /
`data_layer` 三类清零**。剩余只有 24 条 `cross_feature_import`（既有 providers 接缝，
按 AGENTS.md 是 sanctioned 形态）与 2 条 `directory_file_cap`。

### 验证

`flutter analyze` 全仓干净；`test/customizer`、`test/core/composition`、
`test/today`、`test/record`、`test/review` 全绿。
## feat(generative): A7a —— 生成式 UI 的 catalog 与渲染链路

### 为什么

组件化计划 A7 的第一段（`plans/2026-10-31-a2ui-generative.md`）：agent 按用户的
文字指示现场拼装展示性界面。`bc6b3c0db` 只落了 `core/composition/genui/` 的渲染引擎
接缝，没有任何调用方——本提交把**调用它的那一半**补齐：准入规则、生成态、结果持久化、
`generative.<surface>` 组件、首批三个领域 item。

### 落地

- **`lib/features/generative/`**（四层）：
  - `domain/services/catalog_policy.dart` —— 准入规则纯函数。白名单之外一律拒绝；
    **任何数值属性直接判为编造**（这是计划 §6「AI 编造健康数值」红线的可执行形态）；
    引用键必须在 `DataScope` 里存在。`id` / `component` 是协议字段，不参与白名单检查。
  - `domain/services/item_catalog.dart` —— `metric_card` / `trend_chart` / `finding`
    三条政策。`finding` 只有 `findingId`，没有任何文案属性进白名单。
  - `domain/entities/generation.dart` —— `GenerationState` 四态 + 消息序列值类型。
  - `application/orchestrators/generation_session.dart` —— 生命周期与「恢复默认」
    结论。任一政策变体零违规即放行，否则报违规最少的那组，避免「缺 kind」与
    「缺 kinds」互相矛盾地同时报出。
  - `data/datasources/generation_cache.dart` —— 消息序列落 `KvStore`（键仍为
    `genui.<surface>.surface`）。
  - `presentation/` —— 注册 `generative.<surface>`；`generative_surface.dart` 是三态入口。
- **`lib/core/composition/genui/`**：`data_scope.dart` 下沉到
  `lib/shared/domain/generative/`（规则层要用它，而 `domain/` 不允许 import `core/`）；
  `store.dart` 移到 `features/generative/data/`（持久化要碰 `KvStore`，不适合留在 core）；
  `surface.dart` 的 `Surface` 改名为 `GenerativeSurfaceRenderer`——`genui` 的 `Surface`
  与 Material 的 `Surface` 同名，直接导出会让调用方两边打架，而 feature 本就不该
  import `genui`。错误边界补上「`build` 异常包不住」的说明（真正兜底的是 `genui`
  的 `FallbackWidget`）。
- **`lib/app/composition/generative/catalog.dart`**：组装带领域 item 的 catalog。只有
  这里允许同时看见 `genui`、review 的组件与 core 契约。
- **`lib/app/composition/components/registry.dart`**：注册生成式组件 + 覆盖
  `generativeCatalogProvider`。

### 三个设计结论（原计划 §7 的待确认项）

1. **每 surface 一个** `generative.<surface>`。生成结果按 surface 存，渲染引擎也按
   surface 一份；全局共用会让「这块结果属于哪个页面」变成运行期问题。
2. **没有生成结果时不渲染**（`SizedBox.shrink`，尺寸为 0），生成中给骨架，有结果才
   渲。默认布局因此干净，首次生成之后才会出现。失败不是第四种结论：有上一份就继续
   渲染它。
3. **恢复默认连带清生成结果**。没生成过的用户本来就不渲染，清不清对他们没有可观察
   差异；生成过的用户点「恢复默认」时期待回到刚装好的样子。

### 门禁口径的一处修订

`generative.<surface>` 与 `contract_test` 的「id 首段不得是 surface 名」冲突。按计划
的结论保留该 id 形态，在 `contract_test` 里显式豁免（`isSurfaceScopedGenerativeId`），
并补一条测试断言它必须指向真实存在的 surface——豁免的是形态，不是写错的 id。

`--clean-layers` 的 `presentation_layer` 那条（`59635f7c2` 把运行时开关从
`core/ai/` 移到 `core/experiments/runtime/` 后，白名单仍指向旧路径）一并修掉：
白名单改为 `lib/core/experiments/`。

### 验证

`flutter analyze` 干净；`flutter test` 全绿（含新增 `test/generative/` 的规则、会话、
渲染三组）；`--clean-layers` 回到 26 条存量（无本 feature 的违规）；`arch_guard`
循环依赖与本次改动无关。

## feat(generative): 接上后端生成端点（A7b）

### 为什么

A7a 只落地了渲染链路：`generativeStateProvider` 恒为 `GenerationIdle`，页面上什么都
不出现，因为当时后端还没有生成端点。Lucent 的
`POST /layouts/:surface/generate` 已实施完毕并导出到 `openapi.json`，本次把客户端那一
半接上：SSE 消费 → 生成态推进 → 消息重放 → 写入缓存。

### 落地

- **`data/datasources/generation_remote.dart`（新）** —— 用 `LucentSseClient.postJson`
  消费 SSE，按 `event` 名分派四帧。帧名收进 `GenerativeSseEvents` 常量，不散在
  `switch` 里：它们是跨仓契约，漏改一处的后果是事件被静默跳过。
- **`domain/repositories/generation.dart`** —— 接口加 `generate(GenerationRequest)`，
  返回 `Stream<GenerationStreamEvent>`（`chunk` / `result`）。不用 `TaskEither`：
  增量必须边到边消费，而 `TaskEither` 只有一个终值。
- **`data/repositories/cached_generation.dart`** —— 收口两条腿：`generate` 走远端，
  `read`/`write`/`clear` 走本地缓存。`GenerativeMessageCache` 相应**不再实现仓储接口**
  ——让缓存去实现含 `generate` 的接口就得写一个永远抛异常的桩，那是把「未实现」伪装
  成「实现」。
- **`presentation/providers/generation.dart`（新）** —— `generativeStateProvider` 从
  恒 `Idle` 的 `Provider.family` 换成 `NotifierProvider`，由 `GenerationSession` 驱动。
  它同时负责**重放**：渲染层靠 `transport.contextFor(surfaceId)` 取上下文，消息没喂进
  引擎就永远是 `null`，有结果也不渲染。
- **`core/composition/genui/transport.dart`** —— 新增 `feedMessageJson`：服务端
  `chunk` 的 `data` 已是解析好的消息对象，走 `feedJsonLine` 要编码再解码，走
  `feedChunk` 则完全错（那是给未解析文本做增量解析的）。
- **`app/composition/generative/generation_repository.dart`（新）** —— 装配远端 +
  缓存，并把 `Dio` 这个 `core/` 依赖关在组合根里。
- **`presentation/widgets/compose_entry.dart`（新）** —— 触发入口。A7a 的「无结果就
  不占位」在没有入口时是自洽的；接上端点后必须有东西让用户点，否则能力够不到。
  `tab_chrome` 不给入口（服务端会以 400 `GENERATIVE_SURFACE_UNSUPPORTED` 拒绝）。
- **l10n** —— 新分片 `lib/l10n/src/generative_{en,zh}.arb`，并在
  `scripts/l10n/arb_tools.dart` 的 `fragmentRules` 注册（不注册 merge 会丢弃它）。

### 三个判断

1. **`result` 是权威序列，`chunk` 只作渐进反馈**。落盘与重放都用 `result`；只靠
   chunk 拼序列会把半棵树留在屏幕上。
2. **流在 `result` 之前结束 = 失败**。不显式收尾的话页面停在骨架永转圈，而这恰好是
   「服务端中途关连接」的形态。
3. **两条失败路径分开处理**：开流**前**的 400/422 是普通 HTTP 错误，经
   `LucentErrorMapper`；开流**后**的失败才是 `event: error`，走 `mapSseStreamError`。
   混同会让其中一类变成未映射异常。

### 不硬编码

SSE 帧名、路径、surface 名、界面文案全部集中：帧名在 `GenerativeSseEvents`，路径在
`LucentApiPaths.generativeSurface(surface)`（surface 作参数，不拼字面量），文案在 ARB
分片，`tab_chrome` 的可生成性判断复用 `isComposableSurface` 而不是在 UI 里写字面量。

### 验证

`flutter analyze` 干净；`flutter test` 全绿（新增 `test/generative/generation_stream_test.dart`
五条：chunk+result 落地并写缓存、缺 result 保上一份、流早停不停 InFlight、违规整次
失败且不写缓存、坏 chunk 可跳过）；`--clean-layers` 仍是 26 条存量（本 feature 0 条，
过程中出现的一处 `no_throw` 已用 `late` 消除而不是加豁免）。
