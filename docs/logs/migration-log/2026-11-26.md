## feat(generative): A2UI catalog id 改由 `--dart-define` 提供

`GenerativeCatalog.luminousCatalogId` 原本是写死的 `https://luminous.app/a2ui/catalog/v1.json`
——那个域名是迁移时凭空写的，没有人确认过归属。catalog id 是**对外发布的标识符**
（出现在模型产出的每一条 `createSurface` 里），选它属于部署决定，不该由代码替部署方
声称一个域名。

### 变更范围

- `EnvKey.a2uiCatalogId`（`A2UI_CATALOG_ID`）+ `EnvReader` 分支；与 Lucent 的服务端
  变量**同名**，因为两边必须同值：服务端据此告诉模型写什么，渲染端按它找已注册的
  catalog，不一致时整批组件被按「不属于本 catalog」拒绝。
- `GenerativeCatalog.catalogId` 由 `static const` 改为读 env 的 getter；未配置时用
  `defaultCatalogId = urn:a2ui:catalog:luminous:v1`。选 URN 而不是 URL 是刻意的：
  A2UI 只要求它是字符串标识（约定写成 URI 以免撞名），URN 不声称任何域名所有权。
- 空值兜底放在**使用点**而不是 `EnvReader.string(fallback:)`：后者只在
  `String.fromEnvironment` 分支套兜底，`setTestValue` 分支原样返回空串。这一条是
  `catalog_id_test.dart` 抓出来的——catalog id 变成空串会让 surface 建不出来。
- `.env.example` / `.env.e2e.example` 补 `A2UI_CATALOG_ID`（留空即默认 URN），并写明
  必须与 Lucent 同值。
- 三个既有生成式测试里写死的 catalog id 改为引用
  `GenerativeCatalog.defaultCatalogId`，否则它们渲染的 surface 与本 build 注册的 catalog
  对不上。

### 顺带修掉的既有缺陷

`.env.example` 里 `LUMINOUS_EXPERIMENTAL_AI_RUNTIME` / `LUMINOUS_AI_RUNTIME_PROVIDER`
两条**代码从来没读过**（只在旧归档里出现）；代码读的是
`LUMINOUS_EXPERIMENTAL_RUNTIME_ENABLED` / `LUMINOUS_RUNTIME_PROVIDER`，CI 文档表也是后一组。
照抄 example 等于没设。已把 example 对齐到代码实际读取的名字。

### 验证

- `flutter analyze`：No issues found。
- `test/generative`：35 个用例通过；新增 `catalog_id_test.dart` 4 例（默认是 URN、
  读 `A2UI_CATALOG_ID`、build 出来的 catalog 与文档都带该 id、空白值回落默认）。
- 未跑全量 `flutter test`。

## feat(llama_native): 端侧 LLM 推理包，Dart 侧分层落地

新增 `pkgs/llama_native`：基于 llama.cpp 的端侧推理包。**本轮只做 Dart 侧，原生库尚未
构建**，因此包还不能真正推理——剩下的工作记在 `docs/TODO.md` 的对应小节。

### 分层（Clean，`app → domain/ports ← data`）

| 层 | 内容 |
| --- | --- |
| `domain/` | 纯 Dart：`GenerationOptions` / `EngineOptions` / `ModelInfo` / `ChatMessage` / `GenerationResult`、`LlamaFailure`（稳定 kind）、`LlamaEngine` 端口、`CollectGeneration` 与 `fallbackChatPrompt` |
| `data/ffi/` | `llama_shim.h` 的机械映射，零逻辑 |
| `data/isolate/` | 跨 isolate 词汇（`worker_protocol`）+ worker（唯一持有原生句柄） |
| `data/worker/` | 主 isolate 侧会话（`WorkerConnection`） |
| `data/repositories/` | `LlamaCppEngine`：domain ⇄ worker 翻译 |

`domain/` 不含 FFI、isolate 或 I/O，所以 `test/domain_test.dart` 的 12 个用例**不需要
原生库或模型文件**。这也是分层的主要收益：取消语义、缺模板的回退、参数校验这些规则
都是毫秒级可测的。

### 三个决策及理由

1. **C shim 而非直接绑 `llama.h`**：llama.cpp 的 C API 在版本间改名、改结构体
   （`llama_load_model_from_file` → `llama_model_load_from_file`，sampler 链整体替换）。
   直接绑定会让升级表现为段错误而非编译错误。`src-native/llama_shim.h` 是约 10 个
   **我们控制的**函数。
2. **推理必须在 worker isolate**：`llama_decode` 每 token 阻塞数百毫秒，在主 isolate 上
   整个生成过程 UI 冻住。
3. **原生句柄只在 worker**：`Pointer` 不能跨 isolate 传递，共享句柄是未定义行为。

### 编写中撞到并修掉的问题

- `NativeCallable<T>` 的类型名写错（`NativeTokenCallback` → `TokenCallbackNative`）。
- `StreamController.addError()` 返回 `void`、`close()` 返回 `Future`：前者不能包
  `unawaited`（会报 `use_of_void_result`），后者必须包（否则 `discarded_futures`）。
- `WorkerConnection.close()` 原本先置 `_closed = true` 再发 dispose，导致 `_send` 直接
  拒绝、dispose 永远发不出去；改为先等 ack 再置位。
- 模块级 token sink 会在 `generate` 结束后残留，下一次生成继承一个已无人监听的端口；
  改为在 `finally` 里清空。
- `pubspec.yaml` 的分层写作 `domain/errors` 与实际 `domain/failures` 不一致。
- `.gitignore` 的 `/build/` 只锚定根目录，子包测试产生的 `pkgs/*/build/` 会漏进提交；
  改为 `**/build/`。

### 验证

- `flutter analyze`（包内）：No issues found。
- `flutter test`（包内）：12 个通过，覆盖参数校验、`isRetryable`、取消保留部分文本、
  流错误传播、回退提示词、未加载守卫。
- `dart run scripts/docs/verify.dart --verify`：通过。

`docs/TODO.md` 的「端侧 LLM」小节，按依赖顺序排列。

## ci(luminous): 门禁步骤放开阻断，失败结论收口到末尾汇总

### 变更范围

`.github/workflows/ci.yml` 的 `verify` job 原有 13 个串行步骤，`flutter analyze` 一旦
报错，后面 `flutter test` 与 KMP host tests 全部跳过——拿到的是「分析有错」，却看不到
「测试是否也坏了」。反过来也一样。一次 push 只能得到一个失败面，修完再等下一轮。

改法是把四条**彼此独立**的检查改成可失败不阻断，末尾加一步汇总：

| 步骤 | id | 改动 |
| --- | --- | --- |
| Verify generated docs | `docs` | `continue-on-error: true` |
| Analyze | `analyze` | `continue-on-error: true` |
| Clean Architecture violations | `clean_layers` | 保留原有 `continue-on-error`，补 `id` |
| Run tests | `test` | `continue-on-error: true` |
| Run KMP host tests | `kmp` | `continue-on-error: true` |
| **门禁汇总** | — | 新增，`if: ${{ !cancelled() }}` |

### 两个不能想当然的点

- **必须读 `steps.<id>.outcome`，不能读 `conclusion`**。`continue-on-error` 下
  `conclusion` 恒为 `success`，只有 `outcome` 保留 `failure`。用错就等于把门禁静音了。
- **`id` 不能用连字符**。`steps.clean-layers.outcome` 里的 `-` 会被表达式解析器当作减号，
  workflow 在启动前就被判为 invalid（[Unexpected symbol '-' 的成因](https://latchkey.dev/learn/github-actions/github-actions-unexpected-symbol-expression)）。
  所以这一步的 id 用 `clean_layers`；`name` 保持原样不动，日志与界面上看到的仍是
  "Clean Architecture violations"。
- **汇总用 `!cancelled()` 而非 `always()`**。手动取消 run 时不该再冒出一个「汇总失败」，
  那会把「用户取消」伪装成「代码坏了」。

汇总步骤本身不带 `continue-on-error`，所以失败会照常让 job 变红——这正是要的
「跑完再报错」，而不是「假装成功」。

汇总脚本区分三种 outcome：`success` 放行；`skipped` 报「前置步骤失败，未运行」并给出
上游日志指引；其余按失败处理。前置步骤（ARB 合并 / bootstrap / 子包依赖解析）挂掉时
四条检查会是 `skipped`，若一律报「失败」会误导排查方向。

### 保持串行的部分

`Merge ARB fragments` → `Bootstrap generated sources` → `Build generated API client`
是四条检查的**共同前置**（build_runner 要跑几分钟）。拆成独立 job 等于把这套跑两遍，
35 分钟预算直接翻倍，所以仍留在同一 job 内、仍按顺序阻断。改动只针对检查项本身。

### 验证

- `yaml.safe_load` 解析通过；job 内 14 个步骤，5 个带 `id` 的检查项
  `continue-on-error` 均为 `true`，汇总步骤 `if` 为 `${{ !cancelled() }}`。
- 汇总脚本在本地用 bash 跑了三条路径：全部 `success` → exit 0；
  混合 `failure` → exit 1 且逐条列出；全部 `skipped` → exit 1 且报「未运行」。
- 未在真实 runner 上跑过（需推送到 GitHub 才能看到 Actions 的实际行为）。

## refactor(llama_native): 核心改用 Rust（llama-cpp-2 + flutter_rust_bridge）

上一轮的实现是「Dart FFI + 手写 C shim」。本轮换成 Rust 核心，理由不是语言偏好：

- `llama-cpp-2` 从 vendor 的 llama.cpp 源码生成 bindings，上游改名/改结构体是**编译
  错误**而非运行时段错误——这正是那份手写 shim 存在的唯一目的，于是 shim 整个删掉
  （`src-native/`、`data/ffi/`、`data/isolate/`、`data/worker/` 全部移除）。
- 模型与 context 的生命周期由所有权系统管住，不需要 Dart 侧手工配对 `malloc`/`free`
  与维护 pending 调用表。
- `flutter_rust_bridge` 生成类型安全绑定，Dart 看到的是 `Future` / `Stream` / 类型化
  错误，不是指针。

### 分层没变

`app → domain/ports ← data` 保持原样。domain 层（实体、`LlamaFailure`、`LlamaEngine`
端口、`CollectGeneration`）**未改动**，因为它本来就不认识底层语言。

新增的接缝是 `LlamaBridge`：`RustLlamaEngine` 依赖这个接口而不是直接调生成代码。

### 为什么 `LlamaBridge` 要可注入

生成代码是机械命名的自由函数，直接调用会让 engine 无法脱离原生库测试，且每次重新
生成都波及仓库层。把它做成接口后：

- `RustLlamaEngine` 的全部逻辑（释放态守卫、空输入拒绝、错误翻译、流打平）用 fake
  就能测，**不需要模型文件、原生库或 codegen**——新增的 10 个 engine 测试跑在
  毫秒级；
- 生成物改动只影响一个适配类。

这不是为测试而测试：`generate` 的语义是「失败可以发生在已经产出文本之后」，这条规则
只有能构造「先给两个 token 再抛错」的 fake 才能验证。

### 本轮撞到并修掉的问题

- `flutter_rust_bridge_codegen` 未安装（`dart run` 找不到），需 `cargo install`。
  没等安装，改为把接缝抽出来，让包当前就能通过静态分析与测试。
- 端口接口原本有 `load(modelPath)`，但 Rust 侧是「加载即返回会话」，两者语义冲突；
  删掉 `load`，改为 `info()` + 构造时加载。
- `EngineOptions` 作默认参数值时不是 const 构造 → `non_constant_default_value`，
  改为可空参数 + 用时兜底。
- 模块级 token sink 的传端口方案随 isolate 层一起删除；Rust 侧用 `StreamSink`。

### 验证

- `flutter analyze`（包内）：No issues found。
- `flutter test`（包内）：22 个通过——12 个 domain + 10 个 engine（fake bridge），
  覆盖释放态、空输入、流中途失败保留已产出文本、缺模板返回 null、错误变体映射。
- `dart run scripts/docs/verify.dart --verify`：通过。

### 未做

桥接代码生成、Rust 编译、平台工程、模型管理、app 接线。全部在 `docs/TODO.md`
的「端侧 LLM」小节，其中**桥接生成与 Rust 首次编译是当前阻塞点**。
