## feat(generative): finding 改用后端稳定 id 作为引用键

### 为什么

生成式 UI 的 `finding` item 只接受 `findingId`，agent 只能选展示哪一条，文案由
后端原文透传。A7a 阶段后端 findings 没有稳定 id，客户端先用 `ReviewInsightKind.name`
对齐；Lucent 现已给 `ReportFindingDto` 加上 `id`（稳定规则标识），本次改为用真实 id。

### 落地

- `features/review/domain/entities/dashboard.dart`：`ReviewFinding` 增加 `id`。
- `features/review/data/repositories/lucent_dashboard.dart`：映射后端 `dto.id`。
- `features/generative/domain/services/item_catalog.dart`：新增
  `generativeFindingIds` 词表（`hydration_low` / `medication_stable` /
  `sleep_insufficient`），与后端 `FINDING_IDS` 一一对应。
- `app/composition/generative/catalog.dart`：`_FindingSlot` 按 `finding.id` 查找，
  不再拿 `kind.name` 比对。
- `features/generative/presentation/providers/surface_state.dart`：`DataScope`
  补上 finding 条目。

### 顺带修掉一个 A7a 遗留的真 bug

`findingPolicy` 把 `findingId` 声明为 `DataScopeKind.finding` 的引用键，准入要求
引用值存在于 scope 里，但 `generativeDataScopeProvider` **从未声明过 finding 条目**。
结果是任何合法的 `finding` 组件都会被判「引用了不存在的 id」，整次生成失败。本次
补上该条目后，真实 id 才能通过准入。

### 验证

`flutter analyze` 干净；`test/generative` 与 `test/review` 通过；新增三条断言
（词表为 ASCII 下划线命名、每个真实 id 都能通过准入、用 kind 冒充 findingId
会被拒）。全量 `flutter test` 中 `date_picker_test` 两条失败，成因是
`forui 0.27.5` 日历在 1.3x 缩放下的 RenderFlex 溢出，与本次改动无关
（改动文件不含 date/theme/forui，最近两次相关提交均早于本次工作）。

## feat(medicine): 接通 10 个关系图端点，新增 10 个药理分析组件

### 为什么

Lucent 早已提供九个 `medicines/relations/*` 端点与 `medication-overview`，前端一行没调。
这些端点回答的是「为什么冲突」而不是「有没有冲突」：机制通路、共同靶点、四跳级联、
最短路径、酶诱导×底物——平铺的相互作用表结构上表达不了这些。组件化编排（A2–A4）就绪后，
用户可以自己把它们挂成「用药安全工作台」。

### 契约前提（Lucent 侧，同批改动）

十个端点的 `200` 此前只有 `description`、没有 schema，导出物里没有 `content`，
生成客户端把返回值落成 `Response<void>`——**前端就算接了也拿不到字段**。因此先在 Lucent
补齐信封 schema（`{ status, <数据键?> }`）并 `registerResponseSchema`，再重新生成客户端。
详见 Lucent `docs/logs/migration-log/2026-11-01.md`。

### 落地

- `domain/entities/relations.dart`：九个查询的实体 + `GraphQueryResult<T>` 信封 +
  `MedicationOverview`。`GraphQueryStatus` 含 `unknown`（服务端新增状态时按「无法回答」）。
- `domain/services/graph_drug_set.dart`：从用药条目派生 DrugBank id 集合的**纯规则**。
  只收 `DB\d{5}`、去重、排序（稳定 family key）、上限 10，并保留「在册药数」。
  刻意不认识 health_context——`domain/` 只能 import 本 feature 的 domain。
- `data/datasources/medicine_relations_remote.dart` + `mappers/medicine_relations.dart`：
  十个端点各一个薄映射；失败态数据键为 null，**不** `?? const []`。
- `data/repositories/relations.dart`：传输失败折成 `Left`；图不可用的三态是**成功答案**，
  留在 `Right`（它不是「加载失败请重试」，做成分支会让两种语义长成同一张错误卡）。
- `presentation/providers/relations/graph.dart`：`graphDrugSetProvider` 先读快照缓存再
  await；九个查询按入参做 family，挂两个 surface 只发一次请求。
- `presentation/widgets/sections/graph/`：`graph_card.dart` 统一三态渲染，
  `drug_set_sections.dart`（五个无参）、`selector_sections.dart`（五个需入参）。
- `presentation/components/catalog.dart`：十个 `dose.*` id 注册进 registry 与 `owned`。
- 新文案 46 条并入 `lib/l10n/src/medicine_{zh,en}.arb` 片段后 merge + gen-l10n。

### 降级语义（本组组件最不能出错的点）

`ok` + 空数组 = **图上确实没有**（中性措辞）；`notConfigured` / `unavailable` /
`timeout` = **我们无法回答**（警告卡，明写「这不是『没有相互作用』」）。
失败**不返回 `null`**：`ComponentHost` 把 `null` 连间距一起移除，区块消失会被读成
「没有相互作用」。`notConfigured` 不给重试按钮——重试永远不会成功。

另：只有带 DrugBank 编号的药能参与分析，所以组件同时显示「在册 N 种 / 参与分析 M 种」，
避免用户把部分覆盖当成全量结论。

### 默认布局

十个组件**全部不进 medicine 默认布局**，默认页与改造前完全一致。原因：五个需要入参
（避开哪个酶 / 起止药 / 靶点基因）无法自动派生，默认挂上只会是一排空态；且这组卡片
依赖 health_context 快照，默认挂上等于让每次翻页多一条依赖链。「安全工作台」是用户
编排出的一页，不是开发者预设的一页。

  `graph_components_test`），覆盖：失败态不塌成空数组、未知 status 按无法回答、

## 桌面端五个 tab 改为组件网格双列

### 背景

桌面端（宽度 ≥ `Breakpoints.desktop`）的 surface 网格是两列，但 `regular`
尺寸在这两列下**跨满两列**（`ComponentLayout.spanOf`）。五个 tab 的默认布局
此前清一色是不带 `size` 的 `ComponentPlacement`，即默认 `regular`，
于是桌面端实际渲染成一条满宽单列——视觉上就是「手机界面等比放大」。

### 变更

两件事，缺一不可：

1. **各 tab 桌面端统一改走组件网格。** 此前只有 `today` 的桌面端用
   `ComponentHostGridSliver`，其余四个 tab 各自手写 `Row`：`record` 是三栏
   （日历 260 + 主区 + 新建面板 220）、`medicine` 双栏/三栏、`mine` 6:4 双栏、
   `review` 是单列 `ListView` + `ComponentHost`。手写分栏无法被编排页重排，
   也让「桌面端只是把手机界面放大」躲过了组件模型。现在五个 tab 一律走
   `ComponentHostGrid` / `ComponentHostGridSliver`，由视口解析列数。
2. **默认布局把可配对卡片改为 `compact`。** 桌面端网格是两列，而 `regular`
   在两列下**跨满两列**（`ComponentLayout.spanOf`），所以不改尺寸的话即使走网格
   也仍是一条满宽单列。改为 `compact` 后才真正两两并排。

另外 `review` 补上了 `DesktopTabShell`：此前它是唯一仍用移动端外壳的 tab，
桌面端没有统一标题栏、也不吃内容区 maxWidth 约束。

按 tab：

- `today`：问候、主/次建议、指标摘要、健康事件、体征观察；横幅与快捷操作条保持
  `wide`。
- `record`：日期、快捷录入、筛选、时间线。
- `medicine`：药品箱、用药记录、安全引擎、快捷操作（与关系图的 10 个组件互不影响，
  那 10 个本来就不进默认布局）。
- `review`：覆盖率概览、值得注意、事件四段、单/多维趋势；周期开关、事件头部与
  历史列表保持通栏。
- `mine`：个人提醒、归档摘要、隐私提示、提醒设置、账号安全。

移动端不受影响：`mobile` 只有一列，`spanOf` 对所有尺寸都返回 1。

### 已知功能损失（record）

`record` 原有手写桌面布局里直接渲染了 `RecordMonthCalendarPanel`（月历，支持把
时间线卡片拖到某一天改日期）和 `RecordNewEntryPanel`。组件目录里没有对应组件，
改走网格后这两个面板在桌面端不再渲染，**日历拖拽改日期这一交互在桌面端消失**。
需要补一个日历组件才能恢复；在此之前桌面端建记录只能走时间线/快捷录入入口。

### 验证

- `flutter analyze`（全仓库，含 `test/`）干净。
- `dart format` 已应用。
- 测试未运行：期间 `sqlite3` native-assets 依赖 `pubspec.yaml` 固化的本地镜像

## fix(customizer): 编排草稿读取跨 provider 销毁边界导致崩溃

### 为什么

`EditSessionNotifier.begin()` 先 `await StartDraft(...).call(catalog)`（cache-first
仓储，可能附带一次远端刷新），返回后才写 `state`。`editSessionProvider` 是
autoDispose，await 期间用户退出编排页（或 provider 因依赖变更重建）就会销毁 Ref，
随后写 `state` 直接抛 `UnmountedRefException`：`Cannot use the Ref of editSession
after it has been disposed`。

缓存命中且无远端刷新时 await 在退出前就返回，所以现场表现是偶发；只在「进入编排
后立刻返回/手势退出」以及「读取未完成时 provider 重建」两条路径上稳定复现。

### 落地

- `providers/draft.dart`：`build()` 里注册 `ref.onDispose`，销毁时置
  `_disposed` 并清空 `_session`；`begin()` 在 await 之后用
  `_isCurrent(generation)`（`_disposed` / `ref.mounted` / 代次三重判定）决定是否
  继续。加入代次而不只依赖 `ref.mounted`，是因为 provider 重建后 Notifier 实例与
  旧闭包共用同一份字段，而 `ref` 已换成新的、`ref.mounted` 重新为 true——旧会话
  的读取结果会覆盖新会话草稿。
- 状态写入收敛到 `_publish()`，`applyEdit` / `resetToDefaults` / `resetToInitial`
  一并受益：拖拽落点等手势回调可能晚于页面销毁，同样会撞上未挂载的 `state` setter。
- `pages/page.dart`：postFrameCallback 先判断 `mounted` 再 `ref.read`——
  `ConsumerState.ref` 在 dispose 后不可用，同一帧内被弹掉时这里会先炸，
  与 provider 侧的防护是不同层级。

### 验证

按本次任务指示未运行 `flutter analyze` / `flutter test`。改动仅限
`presentation/` 两文件，无新增依赖、无 l10n 变更、无生成物变更。

## 桌面端视觉方向 P-1：响应式布局改用 fluid_adaptive

### 变更范围

- 新增依赖 `fluid_adaptive ^2.0.0`（MIT，纯 Dart/Flutter，无原生代码，无传递依赖）。
- `LayoutScaleResolver.resolve`：自写的 if 分档链换成
  `ResponsiveBreakpoints.standard.sizeClassFor(width).resolve<LayoutScale>()`。
  四档取值表保留为 `LayoutScale` 常量，分派逻辑交给包。
- 档位阈值改用 Material 3 window size class 标准值 600 / 840 / 1200
  （原为 600 / 960 / 1200）；`≥1400` 不再单列一档，内容上限 1600 兜住。
- `Breakpoints.tablet`(960) 更名为 `Breakpoints.expanded`(840)，11 处调用点同步迁移。
  改名理由是去掉「平板」这一设备意象——同一宽度在桌面窗口窄化时同样命中。

### 为什么换

`ResponsiveContentFrame` 只是 `ConstrainedBox` + `Center`，`LayoutScaleResolver`
是一条手写 if 链：两项都没有布局算法，却要长期自己维护阈值与档位语义。
`fluid_adaptive` 提供 window size class、`resolve<T>()` 的就近回退、
`ResponsiveCenter` 等内容宽度预算工具，且阈值是包的标准值。

### 验证

- `flutter analyze` 全仓 0 issue。
- 定向测试全通过：`test/core/design/`、`test/desktop/desktop_widgets_test.dart`、
  `test/core/widgets/responsive_content_frame_test.dart`。
- 新增 `LayoutScaleResolver.resolve` 档位边界测试（原先 `resolve` 零覆盖）。
- 新增断言：`Breakpoints` 三个主分档必须等于 `ResponsiveBreakpoints.standard`
  的阈值，防止两套阈值再次漂移。

### 已知影响

- 840–959 区间从「平板档」变为「小桌面档」（`maxContentWidth` 1040 提前生效），
  该区间的页面留白与内容宽度会变化。手机端（<600）不受影响。
- 桌面档 `pageHorizontalPadding` 由 `xl3`(24) 回到 `xl2`(20)，与超宽档合并。

## 桌面端视觉方向 P0：三层底色（侧边栏 / 画布 / 卡片）

### 变更范围

- `SurfaceTokens` 新增 `sidebarBackground`，并把「页面底色」与「卡片」的
  相对顺序固定为 `sidebar < scaffold < card`。
- `family.dart` 的 `scaffoldStyle.sidebarBackgroundColor` 改用该 token
  （原与 `backgroundColor` 同值）。
- `features/shell/presentation/page.dart` 的桌面侧边栏不再用 `colors.background`
  覆写 `FSidebar` 的 decoration，改读主题下发的侧边栏底色。

### 为什么

桌面端侧边栏与内容区同色，整屏层次只剩 1px 边框在撑；而主题里的
`sidebarBackgroundColor` 又被页面的 `decoration` 覆写，等于设了也不生效。

### 实测修正的两处方向性错误

1. **亮色**：`colors.background` 是纯白，比 #FAFAFA 的页面**更亮**，
   拿它当侧边栏底色会让导航比页面浅。改为由 scaffold 派生。
2. **暗色**：`card`(#171717) 比 `background`/`secondary` 的 50% lerp(#181818)
   **更暗**，旧公式让页面亮于卡片，卡片沉进页面。scaffold 改为由 `card`
   向 `background` 派生，保持 `background < scaffold < card`。
   侧边栏在暗色下朝 `background` 方向走才是"更深"——朝 `secondary` 是变亮，
   与直觉相反。

### 验证

- 新增 `test/core/design/surface_test.dart`：固定三层顺序（亮/暗各一遍），
  并用「background→card 区间的 20%」作为最小可辨差值——暗色可用区间只有约
  0.006，绝对阈值不适用。
- `flutter analyze` 全仓 0 issue；`test/core/design/`、`test/desktop/`、
  `test/core/widgets/responsive_content_frame_test.dart` 定向测试全通过。

### 已知影响

侧边栏底色在亮色下由纯白变为一档灰，暗色下加深；卡片在暗色下相对页面
变为可浮起。手机端 `sidebar: null`，不受影响。

### 补充裁决：内容区平铺，不做卡片套卡片

曾尝试把桌面内容区裁成圆角白卡（内缩 6 + `ClipRRect` + 卡白底），
作为「画布」承载其上的卡片。**已否决**：内容区变白之后，卡片刻度与画布同色，
白卡上的白卡只能靠边框区分，等于把层次又加了回去，且构成卡片套卡片。

最终形态：内容区**平铺** `scaffoldBackground`，层次完全由 `SurfaceTokens`
的三层色差表达（`sidebar < scaffold < card`）。承载结构（圆角/内缩）不参与分层。

## 桌面端视觉方向 P3：行高按平台分支

### 变更范围

- `_flattenLineHeight` 增加 `touch` 参数：body 字号在触屏平台保持 height 1.0，
  桌面平台保留 Forui 的 leading；display 字号两端仍压平。

  web 目标是手机浏览器，桌面 web 由独立的 Next.js 客户端承担（ADR-0008）。

### 为什么

把**每一档**行高压成 1.0，理由原本是手机密度：中文手机应用（微信、美团）
的密度来自文本框本身而不是行距。这条理由在手机上成立，到桌面上不成立——
桌面内容列是「被阅读的文档」，body 行高 1.0 时中文没有上下伸部余量，
多行文本会糊成一块。display 字号短且结构性，两端压平都成立。

### 验证

- 新增 `test/core/design/typography_leading_test.dart`：手机 body = 1.0、
  桌面 body > 1.2、display 两端 = 1.0。
- `flutter analyze` 0 issue；`test/core/`、`test/shell/`、`test/desktop/`、
  `test/a11y/`、`test/features/`、`test/today/`、`test/mine/` 定向测试全通过。

### 已知影响

桌面平台下面板/卡片的高度会随行高增加而变高，这是预期内的密度变化。
手机端渲染不受影响。

## 桌面端视觉方向 P4：窗口下限与滚动条

### 变更范围

- `initDesktopWindow` 最小窗口 480×720 → `Breakpoints.expanded + 120` × 640。
- `MaterialApp.router` 增加 `scrollBehavior`（`_DesktopScrollBehavior`）：
  桌面平台滚动条常驻、宽 10、圆角、thumb 用 `outlineVariant`。

### 为什么

- **窗口下限**：480×720 是手机长宽比。窗口能缩到比手机还窄时，桌面布局会塌回
  单列，`Breakpoints` 里所有 ≥600 的分支永远走不到——桌面端的响应式逻辑只存在于
  代码里。下限必须落在「确实算桌面」的区间。
- **滚动条**：Flutter 默认「窄条 + 悬停才显形」在桌面观感上像网页浮层。
  桌面工作台通行做法是常驻细条，它同时是位置指示（拇指长度 = 可视比例）。

### 验证

`flutter analyze` 0 issue；`test/app/`、`test/shell/`、`test/desktop/` 定向测试全通过。

## 修复：桌面双列布局从未真正生效

### 现象

桌面上「优先处理」与「今日摘要」仍然占满整行，尽管默认布局里两者都写成
`ComponentSize.compact`，双列网格也确实按 2 列计算。

### 根因

`_spanOf`（`core/composition/host.dart`）在组件不支持所索求的尺寸时，会**回退到
组件支持的最小尺寸**。这个降级本身是必要的——旧布局不能因为组件改了尺寸集合就
崩掉整页——但它的代价是静默：

```
布局要 compact → 组件 supportedSizes 里没有 compact
→ 回退到组件支持的最小尺寸 regular
→ regular 在双列网格里 span = columns = 2
→ 卡片占满整行，且没有任何报错
```

多数组件没有覆写 `supportedSizes`，落到基类默认的 `{regular}`；而五个表面的
默认布局都是按双列写成 `compact`。于是**双列布局从来没有真正生效过**——网格算
对了列数，每个 `compact` 声明都被逐个降级成满宽。

审计结果：**17 处不匹配，覆盖 today / record / medicine / review / mine 全部五个
表面**。

### 修复

- 为 16 个组件补上 `supportedSizes`（`compact / regular / wide`）。
- `review` 的 `auth.preview_banner` 改为显式 `wide`：它是全程满宽的登录提示条，
  原写法省略 size 用默认 `regular`，靠降级才拿到正确效果。
- 新增 `test/core/composition/placement_size_test.dart`：遍历注册表与各表面默认
  布局，断言每个 placement 索求的尺寸都被其组件声明支持。这条测试在修复过程中
  逐个暴露出全部 17 处（先报 today、再 record、再 medicine…），是本次能一次排查
  干净的原因。

### 验证

- `flutter analyze` 0 issue。
- 定向测试 `test/core/composition/`、`test/today/`、`test/record/`、
  `test/medicine/`、`test/review/`、`test/mine/` 全通过。
- 重新生成桌面档截屏：五个 tab 均正常，渲染文本顺序显示卡片成对出现。

### 已知影响

桌面端卡片宽度发生变化（由满宽变为半宽），这是本次要修复的行为；手机端一列
布局下 `compact` 与 `regular` 的跨度都是 1，观感不变。

## 修复：桌面双列改为纵向流动，阅读顺序与手机端一致

### 现象

双列生效后，卡片按「左右、左右」逐行配对：第 2 个条目跑到右上角、第 3 个
回到左下角。读起来像顺序被打乱——本该往下的内容跳到了右边。

### 根因

`layoutGridRows` 每到 `used == columns` 就切一条新行。这等于把卡片塞进
「每行两项」的表格，而不是按列流动。

### 修复

- **切行判据改为「跨列」**：只有 span 等于列数（独占整行）的条目才切带；
  连续的单列条目留在同一个带里。`used == columns` 不再触发切行。
- **带内按阅读轴均分**：前一半条目给左列、后一半给右列，每列内部是自上而下的
  `Column`。读的顺序是「左列从上到下，然后右列从上到下」，与手机端一路竖直
  的阅读轴一致。
- 没有采用 `i % columns` 交替分配：那会让左列第 1 项的右邻是第 2 项，
  仍然是逐行语义。
- 没有采用「左列堆到等高再填右列」：卡片高度在流式布局里不可知
  （内容决定，且部分组件含内部滚动视图，取固有高度会抛异常），
  按条目数均分是唯一能保持严格阅读顺序的做法。

### 验证

- 探针实测（1000 宽、2 列、8 个单列条目）：
  `c0..c3` 均为 `left=0`（自上而下），`c4..c7` 均为 `left=500`（自上而下）。
- `flutter analyze` 0 issue；`test/core/composition/`（含
  `layout_geometry_test` 的「compact 与 regular 并排」）、五个 feature
  目录定向测试全通过。
- 重新生成桌面档截屏。

### 已知影响

双列下条目分布由「逐行配对」变为「左列一半、右列一半」。条目数为奇数时
左列会多一项。手机端一列，行为不变。
