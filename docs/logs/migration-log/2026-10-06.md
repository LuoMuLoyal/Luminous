# 迁移日志 2026-10-06

## fix(android): release APK 缺失 Flutter 引擎导致启动即崩，改用 --split-per-abi

### 背景

反馈「release 只能在模拟器用、真机打开灰屏」。实测后确认描述反了：debug 正常，
release 在**模拟器与真机都不行**，模拟器上是瞬间闪退。在 `emulator-5554`
（`sdk_gphone64_x86_64`, Android 17）实际复现：

```text
E/FlutterLoader: Caused by: np: Could not find 'libflutter.so'.
                 Looked for: [x86_64, arm64-v8a], but only found: [].
E/AndroidRuntime: FATAL EXCEPTION: main
  java.lang.RuntimeException: Unable to start activity
    ComponentInfo{com.dev.luminous/com.dev.luminous.MainActivity}
```

真机上的「灰屏」是同一崩溃被系统留住的空白窗口，并非另一条渲染路径问题。

### 根因

`android/app/build.gradle.kts` 里两处 ABI 配置叠加，构成自毁组合：

1. **引擎只编了 x86_64**：本地 release 构建走 `--target-platform android-x64`
   （`.dart_tool/flutter_build/<id>/x86_64/app.so` 与
   `android_aot_release_android-x64.stamp` 可证），因此 APK 里唯一的 Flutter
   引擎是 `lib/x86_64/libflutter.so`。
2. **打包规则又把 x86_64 删掉**：`androidComponents.onVariants(withBuildType("release"))`
   中 `variant.packaging.jniLibs.excludes` 排除了 `lib/x86_64/**` 与
   `lib/armeabi-v7a/**`。

唯一存在的引擎 ABI 恰好被剔除规则覆盖 → `lib/` 下只剩第三方 `.so`，
`libflutter.so`/`libapp.so` 全缺 → `onCreate` 抛异常退出。

该剔除逻辑由提交 `b61ef3d9`（2026-09-10 13:05）引入，用于把 debug 崩溃的
修复从全局 `packagingOptions` 搬到 variant 作用域；但 `variant.packaging` 是
**变体级、非产物级**——一旦启用 ABI splits，它对每个 split 产物都生效，
会删掉该 split 自己的引擎。同日 12:58 构建的 release 包（88.8 MB，含引擎）
在改动之前，此后没有 release 验证，回归因此潜伏至今。

同理，`defaultConfig.ndk.abiFilters` 也是错误的所有权划分：fat APK 路径下
Flutter 插件会清空并覆盖它，而 `--split-per-abi` 路径下非空 `abiFilters`
与 ABI splits 冲突（FlutterPlugin.kt 的 `configureAbis` 注释明确警告
abiFilters「would break builds when --splits-per-abi is used due to
conflicting configuration」）。2026-08-28 的归档日志也记过同一结论。

### 变更

- `android/app/build.gradle.kts`
  - 删除 `defaultConfig.ndk { abiFilters += ... }`（ABI 选择归 Flutter 工具）。
  - 删除整个 `androidComponents { onVariants(...) }` 剔除块。
- `.github/workflows/deploy-android.yml`
  - 构建改为 `flutter build apk --release --split-per-abi`，去掉
    `--target-platform android-arm64`（走 fat 路径才需要它）。
  - 上传路径改 `app-*-release.apk`。
  - 新增 `Verify every split APK ships its Flutter engine` 步骤：用 runner 自带的
    `python3` + `zipfile` 逐个校验 `app-<abi>-release.apk` 内存在
    `lib/<abi>/libflutter.so` 与 `libapp.so`，缺失即失败。这类「静默丢引擎」的
    APK 能装能启动、只在 `onCreate` 崩，不做断言无法在上架前发现。
- `README.md`、`.github/workflows/README.md`：同步 release 产物形态与
  「不要再用 `abiFilters`/变体级 excludes 收 ABI」的口径。
- `docs/howto/build-release-artifacts.md`（新增）：发布构建 how-to。此前只有
  `add-new-feature` / `add-localization` / `regenerate-api-client` 三篇 howto，
  发布链路的知识散在 README、`.github/workflows/README.md` 与逐日日志里，出包人
  没有单一入口。本文覆盖三平台出包命令、注入变量、Android ABI 三条硬约束与引擎
  断言脚本，以及「装得上但启动即崩」等六类症状的排查表；`docs/README.md` 索引已加行。

### 验证结论

- `flutter build apk --release --split-per-abi` 通过，产出三个自洽 APK：

  | APK | 包内 ABI | 自带引擎 |
  |---|---|---|
  | `app-arm64-v8a-release.apk`（86.0 MB） | 仅 arm64-v8a | ✅ `libflutter.so` + `libapp.so` |
  | `app-armeabi-v7a-release.apk`（68.7 MB） | 仅 armeabi-v7a | ✅ |
  | `app-x86_64-release.apk`（124.1 MB） | 仅 x86_64 | ✅ |

  每个 APK 仅含自身 ABI，无 fat 冗余；此前失败形态（`lib/` 无引擎）不再出现。
- 模拟器实机验证：arm64 与 x86_64 两个 split 依次 `adb install` 后启动，
  进程存活、无 `FATAL`/`Could not find 'libflutter.so'`，Today 页完整渲染；
  x86_64 包日志确认 `Load .../lib/x86_64/libflutter.so ... ok`，
  `primaryCpuAbi=x86_64`。
- 截图存于工作区根 `screenshots/lumos-release-arm64.png`、`screenshots/lumos-release-x86_64.png`
  （工作区根非 git 仓库，截图不入 Luminous 版本库）。
- CI 新增的引擎断言步骤在本地原样执行：对三个真实产物 `exit=0`；对故意构造的
  「有第三方 .so、无引擎」假包 `exit=1` 并报出缺失的 `lib/arm64-v8a/libflutter.so`
  （正负向均实测，避免断言只做装饰）。
- 新增 howto 通过 `dart run scripts/docs/verify.dart --verify`（链接/front-matter/
  新鲜度/阅读入口/feature README 覆盖）与 `scripts/docs/links.dart`（63 文件无断链）；
  文中引用的引擎断言脚本按原文粘贴执行，对当前三个产物 `exit=0`。

### 遗留

- 真机（vivo X200s）请用 `app-arm64-v8a-release.apk` 复验：模拟器只能证明
  引擎打包正确，无法覆盖真机 GPU/系统差异。
- 本地 release 构建未注入 `--dart-define`，而 `base_url.dart` 在 release 且未
  pin `LUCENT_BASE_URL` 时抛 `StateError`；该异常在 `AuthSessionNotifier.build()`
  的启动路径上被 `ref.read`，引擎问题修复后会成为下一个「打开即崩」的来源。
  真机复验请带 `--dart-define-from-file=.env`（或与 CI 相同的 `--dart-define`）。
- release 未注入 `JPUSH_APP_KEY` 时推送静默禁用，属既有设计，非本次问题。
