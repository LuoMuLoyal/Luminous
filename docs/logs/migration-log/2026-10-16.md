## fix(assistant): FlowUI 深色分支改读 Forui brightness，生产深色下不再失效

### 背景

应用根是 `material_ui` 的 `MaterialApp`，它的 `Theme` 不是 Flutter 框架 `Theme.of` 能取到的
那一个——一次性探针实测：框架 `Theme.of(context).brightness` **恒为 light**，而 Forui 的
`context.theme.colors.brightness` 与 material_ui 自己的 `Theme.of` 都正常报 dark。

`luminousFlowTheme` 用前者选 `FlowColors.light/dark`，于是 **dark 分支在生产中不可达**：
深色下 FlowUI 里未被 bridge `copyWith` 覆盖的字段（`tertiary`、`success`、`warning`、
`inverseSurface` 等）一律取 light 预设。原测试之所以"通过"，是因为它额外套了一层
`Theme(data: ThemeData(brightness: dark))`——这层在生产路径不存在，测试反而把缺陷掩盖了。

### 变更

- `flow_theme_bridge.dart`：`Theme.of(context).brightness` → `context.theme.colors.brightness`。
  该函数里其余 token 早已全部走 Forui，brightness 是唯一漏网的来源。
- `flow_theme_bridge_test.dart`：
  - dark 用例**去掉**那层框架 Theme 包装，与生产路径一致；
  - 新增 light 用例（此前只有 dark 有覆盖）；
  - 新增守卫用例：制造「框架 Theme 报 light + Forui 主题 dark」的矛盾组合，若 bridge 又改回
    读框架 Theme 即失败。

### 顺带修掉测试里的一个恒真断言

原 dark 用例用 `primaryContainer` 判别深浅，但 `FlowColors.dark` 与 `FlowColors.light` 的
`primaryContainer` **完全相同**（都是 `Color(0x14E071A7)`，见 flow_ui 0.3.0
`flow_colors.dart:180,226`）——该断言在 light 预设下也成立，等于没测。已换成 `tertiary`
（light `0xFF3730A3` / dark `0xFF77A8FD`，且未被 bridge `copyWith` 覆盖，能真实反映选了哪个预设）。

### 验证结论

- **回归双向验证**：把源码临时改回 `Theme.of(context).brightness`，守卫用例失败
  （`Expected: 'light|dark|dark'` / `Actual: 'light|dark|light'`）；还原后 6 例全过。
  不是"写了测试"，是确认测试真能抓住这个回归。
- `flutter test test/assistant/flow_theme_bridge_test.dart` 6 例全绿；
  `flutter analyze` 全仓零问题；全量 `flutter test` 3969 例通过（5 skipped 为既有）。
- `dart run scripts/docs/verify.dart --verify` 通过。
- `docs/TODO.md`「`Theme.of(context).brightness` 在本应用深色下恒为 light」条目按完成即删行的约定移除。
- **未在真机复验**：以上结论来自 widget 测试，深色下的实际观感需真机确认。

## feat(auth): OAuth 回调接入原生深链，免手工粘 URL

### 背景

`plans/2026-10-16-client-capability-gaps.md` P0-2。P0-1 只把深链接收能力做出来了，
`useOAuthCallbackHandler` 仍然只认 GoRouter query 参数（web 同页跳回），原生端深链
回来时不会命中。

### 变更

- `presentation/widgets/shared/oauth_deep_link.dart`：`parseOAuthDeepLink` 把深链 URI
  解析成 `OAuthDeepLink{provider, code, state, returnTo}`，复用既有
  `OAuthCallbackParser`（不写第二个解析器）。非 OAuth 路径或缺 code 时返回 null
  （无 code 的链接不可能完成登录，不该报错给用户）。
- `presentation/pages/oauth_callback_hook.dart`：新增 `useOAuthDeepLinkHandler`，
  与 query 参数路径并列；两者最终调用同一组 `complete*Login`。
  - **深链要等会话恢复完成**：`authSessionProvider.isLoading` 期间到达的链接先缓冲，
  等 `isLoading == false` 再消费，否则 redirect 守卫会把用户先带去 home、回调被吞
  （计划风险节已登记该竞态）。
  - `useOAuthCallbackHandler` 内部的三段重复逻辑收敛为一个局部 `complete` 闭包。
- `core/router/routes.dart`：`CoreRoutes` 补 `loginOauthWechat/Qq/Google` 三个镜像常量
  （core 不 import features，沿用既有镜像约定）。
- **自定义 scheme 的 URI 解析坑**：`app://login/oauth/qq` 会被 Dart 解析成
  `host == 'login'` + `path == '/oauth/qq'`，直接取 `uri.path` 匹配不到路由。
  `_callbackPath` 对非 http(s) 的 scheme 把 authority 拼回 path，使单斜杠与三斜杠
  两种写法都能识别。

### 验证结论

- `test/auth/oauth_deep_link_test.dart` 9 例 + `test/core/router/deep_link_test.dart`
  11 例全绿，含单/三斜杠两种自定义 scheme 形态、trailing slash、缺 code、
  `returnTo` 透传、scheme 配置与否的四种组合。
- `flutter test test/auth/ test/core/router/` 316 例全绿（含既有 auth 用例无回归）。
- `flutter analyze` 相关目录零问题。
- **深链域名与 scheme 名仍待定**：仓库内没有任何现存的自定义 scheme 声明
  （Better Auth 时代归档文档里的 `luminous://auth/callback` 已随该功能退役，不作为依据）。
  两者改为 `LUMINOUS_DEEP_LINK_SCHEME` / `LUMINOUS_DEEP_LINK_HOST` 配置项，
  平台侧分别经 Android placeholder 与 iOS xcconfig 注入，默认值仅作占位。
- **未在真机验证端到端回调**：同上，依赖服务端 well-known 文件与最终域名确定。
