# 迁移日志 2026-10-13

## fix(record): 登录提示条在窄屏大字号下不再把文案压成多行

### 背景

真机反馈两件事：记录页顶部登录提示条的右侧按钮「强制一行、字号还很大」，且提示文案被挤成
4 行、整条 banner 被顶高。查 `lib/core/widgets/common/feedback/page_state.dart` 的
`SignInHintBanner`：图标 + 文案 + 按钮三者共处一个 `Row`，文案是**唯一**的可压缩 flex
子节点，因此全部压缩量都落在它身上；窄屏叠加用户自选的大字号档位时被压成多行。

该处此前已修过一次（给按钮加 `ConstrainedBox(maxWidth: 160)` + `Flexible` + 省略号），
但那次只约束了**按钮**的固有宽度，没有解决「文案独自承担全部压缩」这一根因。

### 变更

- `SignInHintBanner`：把图标与文案**先成组**，按钮不再与文案同行争宽；并用 `LayoutBuilder`
  实测单行是否放得下——放得下保持原有并排观感，放不下则让按钮整体落到第二行右对齐。
  文案因此至少能拿到整行宽度，不再被压成多行；按钮标签的 `maxLines: 1` + 省略号保留。

### 验证结论

- 新增 `test/core/widgets/sign_in_hint_banner_test.dart`（4 个用例：393dp/1.15 档单行断言、
  320dp/1.3 档无溢出、宽屏并排、按钮单行省略）。
- **该测试确为有效回归**：把 `page_state.dart` 临时还原到修复前，首条用例失败并报
  `Expected: <1> Actual: <2>`（文案确为 2 行）——即测试真的能抓住这个 bug，而非恒过。
- `flutter analyze` 全仓零问题；`flutter test test/{review,medicine,record,today,core}`
  全绿（含上述新用例）。

## fix(theme): 字阶并入紧凑基线，真机「大一圈」的第二层成因

### 背景

真机与模拟器的差异**不是渲染事故**，也不是模拟器测不出问题——两者跑的是同一套缩放逻辑，
只是真机才是与其他 App 同屏对比的场景。成因有两层：

1. **组件几何（已于 2026-10-12 修复）**：主题此前写死 Forui 的 touch 变体，组件整体大一级
   （field 36→44、item 30→44）。该次已切到 `touch: false`，但日志当时即注明「**未在真机复验**」。
2. **排版字阶（本次修复）**：`lib/core/theme/family.dart` 在 `touch: false` 的同时**显式**传入
   `FTypography.inherit(touch: true)`，即「组件紧凑、文字保持 touch 字号」。实测两个基线相差
   整一档，且**行高同时变大**：

   | 字阶 | desktop（应为） | touch（残留生效） |
   | --- | --- | --- |
   | `body.xs` | 12 / 1.0 | 14 / 1.25 |
   | `body.sm` | 14 / 1.25 | 16 / 1.5 |
   | `body.md` | 16 / 1.5 | 18 / 1.75 |
   | `body.lg` | 18 / 1.75 | 20 / 1.75 |

   行高增幅比字号更明显，这正是「字号看着大一圈、行距还松」的主因。对照 2026-10-12 日志
   「组件紧凑、文字保持可读」的原始取舍——该取舍与同一次改动自相矛盾（同一份主题里一半
   走 desktop、一半走 touch），按**漏改**处置。

### 变更

- `lib/core/theme/family.dart`：`FTypography.inherit(touch: true)` → `touch: false`，
  字阶与组件几何统一到 desktop 基线；文件头注释改记这一结论（含被推翻的旧理由）。
- `lib/core/design/tokens/markdown_style.dart`：`legal` 的正文 `body.sm` → `body.md`
  （长文固定 16px，否则切紧凑字阶后掉到 14px）；引用块同步 `sm` → `md`；标题阶梯保持
  h1=20 / h2=18 / h3=16（w600 区分）。
- `lib/app/bootstrap.dart` 的 `_applyHighContrast` **无需改动**：它原样透传 `theme.typography`，
  自动跟随新基线。

### 验证结论

- `flutter analyze` 全仓零问题。
- **`test/a11y/compact_text_scale_sweep_test.dart` 全 66 用例通过**——含此前一直失败的两个
  RecordPage 用例（360x800 / 320x720 @ 1.3）。即**上一节记录的 `date_bar.dart` 底线溢出
  随之消失**：Forui 的 `_estimateExtent()` 按 style 字号 × scale 计算条目高度，字阶降一档后
  条目自然落入 56dp 容器内，不需要再单独调 `_calendarItemHeight`。
- 全量 `flutter test` 通过。唯一的断言同步是 `test/core/design/markdown_style_test.dart`
  的 legal 正文用例（`sm`→`md`，期望值仍是 16px，并补充「标题高于正文」断言）。
- **未在真机复验**：与上次同样，最终观感需真机确认。

### 另行说明

应用**有意不跟随系统字号**：`lib/app/bootstrap.dart` 用自有的 4 档
（0.85 / 1.0 / 1.15 / 1.3，见 `core/accessibility/settings.dart`）覆盖 `textScaler`。
另外该处当 `accessibility` 尚未加载完成（`null`）时回落 `TextScaler.noScaling`，即首帧
不跟随系统字号——与真机观感无关，但属同一处的既有行为，记录备查。

### 附：`date_bar.dart` 溢出为何被本次改动一并消除

排查中途曾观察到 `flutter test test/a11y` 在 **RecordPage × {360x800, 320x720} @ 1.3**
两个用例失败：

```
A RenderFlex overflowed by 6.0 pixels on the bottom.
  Column: .../features/record/presentation/widgets/sections/date_bar.dart:107
  constraints: BoxConstraints(w=53.8, h=48.0)
```

当时先确认**与 `SignInHintBanner` 的改动无关**（临时还原 `page_state.dart` 后同样失败、
报错点相同；`git diff --stat lib/features/record/` 为空）。字阶并入紧凑基线后两个用例转为通过。

机理：`RecordDateBar` 用 `SizedBox(height: 56)` 包 `FLineCalendar`，但**该高度不决定条目高度**
——Forui 在 `calendar_layout.dart:_estimateExtent()` 里按 **style 字号 × scale + contentSpacing
+ 2×contentEdgeSpacing** 自行估算 extent，行高不参与。实测 style 字号为 `dateTextStyle=14`、
`weekdayTextStyle=8`，spacing=4、edge=13：

- touch 字阶 @1.3：`14×1.3 + 8×1.3 + 30 = 58.6`，而 `_CompactCalendarItem` 自身还有 8dp padding
  与 2dp spacing，条目远超 56dp 容器 → 底溢。
- 紧凑字阶 @1.3：字号降一档后估算值落入 56dp，溢出消失。

因此无需再单独调 `_calendarItemHeight`；`date_bar.dart:42` 那条注释所述「56dp 而非 48dp」的
历史修复方向本身是对的（要抬高容器），只是**真正的杠杆是字阶**，本次改动把它落到了实处。
