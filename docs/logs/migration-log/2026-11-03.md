# 2026-11-03

## fix(ci): Linux 发布构建补 libcurl/zlib 开发包

### 现象

`Deploy Linux`（run `41624513242`，`main`）在 `Build Linux (release)` 步骤失败：

```
CMake Error at /usr/local/share/cmake-4.4/Modules/FindPackageHandleStandardArgs.cmake:290 (message):
  Could NOT find CURL (missing: CURL_LIBRARY CURL_INCLUDE_DIR)
Call Stack (most recent call first):
  /usr/local/share/cmake-4.4/Modules/FindCURL.cmake:291 (find_package_handle_standard_args)
  .../build/linux/x64/release/_deps/sentry-native-src/CMakeLists.txt:493 (find_package)
Unable to generate build files
```

### 为什么

- `sentry_flutter` 的 Linux 插件在 CMake configure 阶段用 `FetchContent` 拉取
  `sentry-native`（9.24.0 锁 0.15.2）并**在本机编译**。这层原生 SDK 不由 Flutter
  工具链提供，它的系统依赖必须由 workflow 自己装。
- sentry-native 在 Linux 上默认 `SENTRY_TRANSPORT=curl`，走
  `find_package(CURL REQUIRED)`；插件又把 `SENTRY_BACKEND` 固定成 crashpad，
  而 crashpad 在 Linux/macOS 上要求系统 zlib（`find_package(ZLIB REQUIRED)`）。
- 原 apt 列表覆盖了 GTK / secret / gstreamer / sqlite / OpenSSL，唯独没有 curl
  开发包。runner 镜像（`ubuntu-26.04`）只带 curl 运行时，不带 `curl/curl.h` 与
  `libcurl.so` 链接名，于是 configure 阶段直接失败。

### 落地

- `.github/workflows/deploy-linux.yml` 的 `Install Linux desktop dependencies`
  增加 `libcurl4-openssl-dev zlib1g-dev`。
- 在 step 注释里写明两者是 sentry-native（curl transport + crashpad backend）的
  构建期硬依赖，避免以后按「看起来和 Flutter 无关」再被删掉。
- 不动 `runs-on`、Flutter 版本、生成物前置步骤与产物校验：问题只在系统依赖面。

### 验证

- workflow YAML 解析通过，`build-linux` 仍是 11 个 step。
- 包名对照 Ubuntu 26.04（resolute）包索引确认存在：`libcurl4-openssl-dev` 提供
  `/usr/include/curl` 与 `libcurl.so`（`FindCURL` 的两个 required var），
  `zlib1g-dev` 提供 `zlib.h` / `libz.so`。
- 依据 sentry-native 0.15.2 README「crashpad backend 需要 zlib；Linux / macOS
  需要 libcurl」与插件 `sentry-native/sentry-native.cmake` 的 `find_package` 路径确认。
- 真实构建仍需在 runner 上手动触发 `workflow_dispatch` 复验：本地是 Windows，
  没有 Linux 桌面工具链，configure 失败只在 Linux 上复现。

## fix(ohos): 本地 HAP 构建补齐 Web 生成物重建与 canvaskit 裁剪

### 为什么

本地 `python scripts/ohos/build_hap.py` 与 CI 的 Web 制品流程有两处口径不一致：

- **构建期产物不重建**：`web/drift_worker.js`（`dart compile js` 产物）与
  `web/sqlite3.wasm`（sqlite3.dart 的 Release 资产）都被 gitignore，CI 每轮现场生成，
  本地只做 `is_file()` 存在性检查。改了 `web/drift_worker.dart` 或升级 `sqlite3` 包后，
  本地会把**上一轮的旧文件**打进 HAP，且没有任何提示。
- **不裁 canvaskit**：`deploy-harmonyos.yml` 上传前会删 `skwasm*` / `wimp*` 与所有
  `.js.symbols`；本地脚本原样拷贝 `build/web`。壳内钉死 canvaskit 单渲染器，这两类
  渲染器永远用不到，实测在 HAP 里白背约 20 MB。

另外 HAP 产不出可安装包的签名步骤此前没有任何文档承接（`signingConfigs` 为空，
hvigor 只 WARN `Will skip sign`）。

### 落地

- `scripts/ohos/build_hap.py`：
  - 新增 `generate_web_assets()`：`flutter build web` 之前先 `dart compile js` 编译
    drift worker、跑 `scripts/web/fetch_sqlite3_wasm.py` 按 pubspec 的 `sqlite3` pin
    下载并校验 wasm；`--skip-web` 时用 `sync_generated_assets_into_build_web()` 把重建
    结果同步进已有 `build/web`。
  - 新增 `trim_canvaskit()`：递归删 `.js.symbols`、删顶层 `skwasm*` / `wimp*`，保留
    `canvaskit/` 与 `canvaskit/chromium/`、`canvaskit/webparagraph/` 各能力档实际产物。
  - docstring 说明这两步是构建硬依赖、且顺序必须在 `flutter build web` 之前。
- `docs/howto/build-release-artifacts.md`：标题扩到 HarmonyOS，新增 HarmonyOS 一节
  —— 一条命令的构建流程、脚本内部顺序、签名（DevEco 自动签名 / AGC 证书 + Profile /
  `hap-sign-tool` 命令行）、安装与排查表；front-matter `updated` 同步。

### 验证

- 全量构建（release）：`flutter build web` 约 110s → 三条产物断言通过 →
  canvaskit 36.1 MB → 15.9 MB → rawfile 平铺 669 文件 → hvigor `BUILD SUCCESSFUL`；
  HAP 从 66.8 MB 降到 46.7 MB。
- `--skip-web` 复用路径：两个构建期产物重建并同步后 6.9s 出包，HAP 46.7 MB。
- 解包复核 HAP：`resources/rawfile/` 下 canvaskit 只剩 6 个文件
  （canvaskit / chromium / webparagraph 的 js + wasm），`skwasm`、`wimp`、`.js.symbols`
  均为 0。
- 未做设备侧验证：`hdc list targets` 为空；产物仍未签名，签名与安装步骤已写入 howto。

## test(design): 桌面档内容宽度断言对齐 1040

### 为什么

CI 的 `Run tests` 从 11-02 起连续失败，最新 run（`develop` @ `dcabed0f8`）挂在 4 条断言上：

- `test/core/design/layout_scale_test.dart`、`layout_tokens_test.dart` 里 3 条断言仍写
  桌面档 `maxContentWidth == 1600`，实际 `1040.0`；
- `test/shell/detail_pane_test.dart` 的关闭态内容宽度用 `> screen * 0.7`：测试屏幕
  1440 下阈值 1008，而新上限 1040 再扣两侧页边距 24 后只有 992。

根因是 `e73690b21`（桌面档截图全量覆盖）把 `_desktop.maxContentWidth` 从 1600 改成
1040：≥ 840 宽度只有一个内容列，避免二级页比一级页宽 200 余像素、法务正文行宽
过长。该 commit 的验证只跑了 `flutter analyze` 与 `test/record` / `test/medicine` /
`test/features/legal`，没有覆盖 design / shell 两组测试，断言因此一直没被同步。

### 落地

- `test/core/design/layout_scale_test.dart`：桌面档 `maxContentWidth` 断言改 1040；
  档位边界改用纵向节奏（`heroVerticalPadding` / `sectionVerticalPadding`）断言——
  小桌面档与桌面档本来就共用宽度上限，`maxContentWidth` 不再能区分两档；顺带把
  「都是 `Spacing.xl2` = 20」的过期注释更正为 `Spacing.xl3` = 24。
- `test/core/design/layout_tokens_test.dart`：`>= 1200` 与 `== 1200` 两条断言改 1040，
  并补 `sectionVerticalPadding == Spacing.xl6` 锚定「确实进了桌面档」。
- `test/shell/detail_pane_test.dart`：关闭态内容宽度改成从设计值推导——
  `min(可用宽度, maxContentWidth) - 2 × pageHorizontalPadding`，不再用 0.7 屏幕比例，
  避免下次上限变化时再出现同类假失败。

### 验证

- 三个受影响文件：`flutter test ...` → 22 条全部通过（含此前失败的 4 条）。
- `flutter analyze`（pre-commit 钩子）0 issue。
- 未跑全量 `flutter test`（按要求只做针对性验证）；其余测试文件未改动。
