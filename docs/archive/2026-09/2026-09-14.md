## refactor(record,health_data): 睡眠时段计算抽为领域服务,payload 键位统一为 startedAt/endedAt

### 背景

睡眠 payload 的时间键位在双仓长期不一致：Lucent 的 DTO 文档把 `startedAt` / `endedAt` 定义为正式键、
把 `startAt` / `endAt` 标为 legacy，但 Luminous 的创建页、编辑页、详情页、NLP 候选编辑器反而一直在
写读 legacy 键；服务端校验器则是两者都读（`startedAt ?? startAt`）。同时「就寝 + 起床 → 跨天时段」
这段时钟算术在创建页与编辑页各写了一份。

NLP 候选编辑器另有隐藏缺陷：用户改动时刻后它把值写成 `{hour, minute}` map，而服务端校验要求时间键
是 ISO 字符串，因此该路径保存必然校验失败。

### 变更

- 新增 `lib/features/record/domain/services/sleep_entry.dart`：`SleepEntryKind`（nightSleep / nap 及线上
  取值与解析）、`computeSleepDurationMinutes`、`resolveSleepWindow`（以**起床日**为归属日解析跨天时段，
  夜间睡眠最多跨一个午夜、小睡禁止跨天）、`validateSleepEntry`（缺时刻 / 起床不晚于就寝 / 小睡跨天 /
  小睡 > 3h / 夜间 > 16h）、`buildSleepPayload`（固定键位 `startedAt` / `endedAt` / `durationMinutes` /
  `sleepType`，加可选 `quality` 与设备侧分期）。
- 新增 `lib/features/record/presentation/utils/sleep_formatters.dart`：`sleepQualityOptions`、
  `formatSleepDurationLabel`、`formatSleepTimeRange`，取代原先散在 `sleep_structured_fields.dart` 与两处
  私有 `_formatDuration` 的重复实现。
- 创建页、编辑页改由领域服务构建 payload；详情页、编辑页、NLP 候选编辑器改读 `startedAt` / `endedAt`；
  NLP 候选编辑器改写时输出规范 ISO 时刻，map 形态的表示整体删除。
- 编辑页保留载入记录的 `sleepType`，避免编辑一条小睡时被改回夜间睡眠；只有时长、没有时刻的设备导入
  记录继续走「仅 durationMinutes」的兜底分支。
- `health_sync` 指纹计算去掉 `?? startAt` / `?? endAt` 回退。

### 验证

- `flutter analyze` 无问题。
- `flutter test test/record test/health_data` 全部通过。新增
  `test/record/domain/services/sleep_entry_test.dart`（跨天解析、小睡同日约束、两类时长上限、payload 键位与
  UTC 时刻往返）；原 `test/record/sleep_duration_test.dart` 由该测试取代删除；编辑页保留 duration-only
  payload 的断言更新为同时写入 `sleepType`。

## feat(record): 睡眠快速录入改为一次性录入

### 背景

睡眠快捷入口此前是两阶段状态机：第一次单击落一条 `sleepEvent: 'start'` 临时事实，第二次单击落
`sleepEvent: 'wake'`，再弹「合并」弹窗把两条合成一条完整睡眠；存在多个进行中的 start 时还要先弹「选择要
结束的睡眠」。目标是一次性录入：表单式收集完整信息，落**一条**记录。

调研（Apple Health / Samsung Health / 华为运动健康的手动录入、Sleep as Android 的 `(+) Add sleep`、
Fitbit / Garmin / vivo 的归属日约定）结论：手动录入主流只收「入睡 + 起床」两个时刻、时长算出来；归属日以
**起床日**最常见（Fitbit `dateOfSleep` 取结束日、Garmin 睡眠记起床日、vivo 官方明文）；但没有任何一家在
录入界面写出这条记录到哪天。因此显式写出归属日是本方案的差异化点。

调研证据（本次决策的外部依据，来源链接随条目保留）：

| 结论 | 来源 |
| --- | --- |
| 平台存储不带日期：HealthKit 只有 start/end 与可选时区元数据；Health Connect 的 `SleepSessionRecord` 只有 startTime/endTime/两个时区偏移/stages | [Sahha 汇总](https://sahha.ai/blog/which-day-does-sleep-belong-to/)、[Health Connect](https://developer.android.com/health-and-fitness/health-connect/features/sleep-sessions) |
| 起床日是最主流的归属约定：Fitbit `dateOfSleep` = 睡眠日志结束那天；Garmin 睡眠记起床日（另加 `calendarDate` 字段声明出现日）；vivo 官方明文「以起床日期做为记录睡眠的日期」 | [Fitbit Web API](https://dev.fitbit.com/build/reference/web-api/sleep/get-sleep-log-by-date/)、[vivo 使用指南](https://health-h5.vivo.com.cn/doc/helpwear/health/sleepWatch.html) |
| 少数派规则：Oura 用 18:00 边界；WHOOP 取消日历日（cycle 从入睡到下一次入睡） | [Oura Nap Detection](https://support.ouraring.com/hc/en-us/articles/1500009653181-Nap-Detection)、[WHOOP 工程博客](https://engineering.prod.whoop.com/dev-platform-2/) |
| 跨天靠时钟算术推断：Samsung「start 的时分晚于 end 的时分 ⇒ 视为前一天开始」 | [Samsung Developer](https://developer.samsung.com/health/blog/en/managing-sleep-data-with-samsung-health-and-health-connect) |
| 手动录入只收两个时刻、时长算出来：Apple Health（Browse → Sleep → Add Data）、Samsung Health（手动插入 session，可选带 stages）、华为运动健康（睡眠 → 手动输入 → 上床/起床时间） | [Levels 转述 Apple Health 流程](https://support.levels.com/article/382-how-to-add-sleep-data-to-the-levels-app)、[华为官方](https://consumer.huawei.com/cn/support/content/zh-cn16058410/) |
| 「整条补录」范式：Sleep as Android 的 `(+) Add sleep`；Oura 不允许新增睡眠，只能拖滑杆**缩短**已有时段 | [Sleep as Android](https://sleep.urbandroid.org/docs/sleep/graph_edit.html)、[Oura 编辑就寝/起床](https://support.ouraring.com/hc/lv/articles/360025445994-Edit-Bedtime-and-Wake-Up-Time) |
| 小睡定义：Oura 记 15 分钟–3 小时为小睡，更长则作为主睡眠段 | [Oura Nap Detection](https://support.ouraring.com/hc/en-us/articles/1500009653181-Nap-Detection) |

由此定下并已落地的约定：一次性录入（类型 + 就寝 + 起床 + 质量 + 备注 → 一条记录，时长算出）、归属日 =
**起床日**且界面显式写出、最多跨一个午夜、小睡为显式类型且同日、小睡 ≤3 小时 / 夜间 ≤16 小时、payload 键位
收敛为 `startedAt`/`endedAt`/`durationMinutes`/`sleepType`，legacy `startAt`/`endAt` 与 `sleepEvent` 临时事实
停用且**不做历史迁移**（产品未上线，无兼容窗口）。

计划文件 `plans/2026-09-14-sleep-quick-entry-one-shot.md` 执行完毕后已删除（结论留在本条目与 feature README）。

## fix(record): 睡眠录入 sheet 贴边、上拖展开,质量改为内联选项

### 背景

一次性录入 sheet 上线后连出四处交互问题：① 类型来回切换只单向回落——切到小睡会换成 13:00–13:30，切回夜间
睡眠却仍停在 13:00–13:30；② sheet 底边与底部 tab 栏之间有一条可见间隙；③ 只能往下拖（关闭），无法往上拖展开；
④ 睡眠质量走 `FSelect` 的**弹出层**，在这个位置空间不足，只露前三行且拖不动。

根因：② 是安全区套了两层——`useSafeArea: true` 时 Forui 只补上/左/右（`SafeArea(bottom: false)`），内部又套了
一层 `SafeArea`，把内容连同背景一起抬离底边；而 Forui 的 sheet 自身不画背景，那条未着色的底边就露出下面变暗的
页面。同时该 sheet 没有复用共享外壳 `SheetSurface`。③ `mainAxisMaxRatio: null` 只解除高度上限，往上拖需要 body
内实现 `DraggableScrollableSheet`（Forui 文档推荐的组合）。① 是两种类型共用一份时间状态。

### 变更

- 时段状态改为**每种类型各存一份草稿**（`_drafts`）：打开时当前类型用预填值、另一种用默认值（夜间 23:00–07:00 /
  小睡 13:00–13:30），编辑写回当前类型草稿，切换类型只换显示哪一份，两边时间互不覆盖。
- 外壳改用共享 `SheetSurface` + `SheetDragHandle`，内部不再套 `SafeArea`，标题居中、padding 与其它 sheet 一致。
- body 包 `DraggableScrollableSheet(expand: false, initial 0.75 / min 0.55 / max 1.0, snap: true)`，其 controller
  交给内部 `SingleChildScrollView`，并按 Forui 注释补 `ScrollConfiguration(dragDevices: touch/mouse/trackpad)`；
  由此可往上拖展开到整屏（往下拖仍是关闭）。
- 睡眠质量由 `FSelect` 弹出层改为**内联 pill chip 行**（较差/一般/良好/优秀，再点一次清除）。
- `docs/reference/design-system.md` 补记该 sheet 外壳与「上拖展开」两条约定；并修正同文件里「`auth_shell.dart`
  仅保留为薄 helper」这句已失效的描述（该文件在 `8aba4b8b` 删除）。

### 验证

- `flutter analyze` 无问题。
- `test/record/sleep_quick_entry_sheet_test.dart` 通过，新增三条断言：每种类型各自保留时段草稿
  （23:30/06:45 切去小睡再切回仍为 23:30/06:45）、上拖后 `SheetSurface` 高度变大、四个质量选项全部内联可见且
  选中后写回 `quality`；另有断言钉住「外层是 `SheetSurface`、内部无 `SafeArea`、路由 `mainAxisMaxRatio` 为 null」。

## fix(record,scan): 底部 sheet 统一收口到共享外壳,修掉底边空隙与拖不动

## refactor(record): 症状与严重度落成 payload 稳定码

（症状链路优化 Phase 1 客户端侧；计划文档 `plans/2026-09-14-symptom-chain-optimization.md`，执行完毕后删除。）

### 背景

症状快速记录把严重度写进记录级 `value`，且是**本地化字符串**（"轻度"）；四个预置症状的 `payload` 为 `null`。
服务端 `today-suggestion/.../deteriorating-trend.service.ts` 的 `extractSeverity()` 只从 `value`/`note` 里猜数字与
关键词，猜不到就回落 1（默认最小严重度）——于是快速录入的每条症状记录一律得 1 分，「症状恶化趋势」规则恒不命中；
`collectors/record.service.ts` 的 `observedValue` 同样取不到值，症状维度覆盖度恒为 insufficient。

同一处还有个会直接坏的缺陷：`symptomEnabledChoices` 存的是本地化标题，`_resolveChoices()` 也按标题过滤——用户
动过「显示哪些症状」之后切换应用语言，目录产出英文标题与存档的中文标题对不上，弹窗会变成空列表。

### 变更

- 新增 `domain/constants/symptom_catalog.dart`：`SymptomCode`（目录码）与 `SymptomSeverity`
  （`mild` / `moderate` / `severe` / `unknown`，词汇与 health_context 的过敏严重度一致）及其 wire 解析；
  `unknown` 表示用户明确判断不了，语义上**不等于** mild，服务端跳过而非记最小严重度。
- `domain/constants/fast_entry_choices.dart`：症状项改为携带 `payload: {'symptom': <码>}`，不再往 `value` 塞严重度
  文案；新增 `recordFastChoiceCode()` 取选项稳定码。
- `fast_entry_dialog.dart`：启用过滤改用目录码；严重度按当前设置补进 payload（`severity`），`value` 只作展示。
- `toggleSymptomChoice`（`shared/copy.dart`）改为按码增删（空集仍表示「全部启用」）；设置页与长按设置弹窗同步按码
  判断选中。
- l10n 新增 `recordFastChoiceSeverityUnknown`（无法判断 / Unknown）。
- `QuickEntryPreferences` 的 `symptomDefaultSeverity` / `symptomEnabledChoices` 注释更新为「四档严重度」「存码」。

### 验证

- `flutter analyze` 无问题。
- `flutter test test/record` 通过。新增 `test/record/domain/symptom_catalog_test.dart`（wire 词汇与 `unknown` 解析）；
  `test/record/domain/fast_entry_choices_test.dart` 的症状组改为断言目录码；`test/record/page_test.dart` 的症状单选与
  多选用例补 payload 断言（`{symptom, severity}`）。

## feat(record): 症状快速记录改为底部 sheet,支持一次点击带严重度与批量撤销

（症状链路优化 Phase 2；计划文档 `plans/2026-09-14-symptom-chain-optimization.md`，执行完毕后删除。）

### 背景

症状此前走通用 `RecordFastEntryDialog`：严重度是**全局默认值**（`_resolveChoices()` 把它盖到每个 chip 上），
想记「重度头痛」得先点一下（落库为默认严重度）再进详情页改；多选批量保存虽然存在，但 `_saveSelectedChoices()`
的 `registerUndo: (_) {}` 让它**没有撤销**。而且这个 dialog 的撤销 toast 用的是 dialog 自己的 context——pop 之后
context 失活，用户点「撤销」会静默失效。

### 变更

- 新增 `presentation/widgets/dialogs/symptom_quick_entry_sheet.dart`：底部 sheet（`SheetSurface` +
  `SheetDragHandle` + `DraggableScrollableSheet`，与饮水/睡眠同一外壳），含严重度四档 pill chip 行（默认取设置项）、

  部分失败时用「已记录 X 项、Y 项失败」文案并仍可撤销成功部分。`_usesLegacyFastEntry` 收敛为只剩情绪与备注。
- `presentation/quick_entry/symptom_flow.dart`：`recordBatch()` 收集每条成功记录对应的撤销动作并合成

  分支、`_saveSelectedChoices`、`_symptomChoiceFor`、多选态按钮与 `_cancel`/`_handleChoiceTap` 的多选分支），
