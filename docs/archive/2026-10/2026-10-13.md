# 迁移日志 2026-10-13

## fix(record): 登录提示条在窄屏大字号下不再把文案压成多行

### 背景

真机反馈两件事：记录页顶部登录提示条的右侧按钮「强制一行、字号还很大」，且提示文案被挤成
4 行、整条 banner 被顶高。查 `lib/core/widgets/common/feedback/page_state.dart` 的
`SignInHintBanner`：图标 + 文案 + 按钮三者共处一个 `Row`，文案是**唯一**的可压缩 flex
子节点，因此全部压缩量都落在它身上；窄屏叠加用户自选的大字号档位时被压成多行。

该处此前已修过一次（给按钮加 `ConstrainedBox(maxWidth: 160)` + `Flexible` + 省略号），
但那次只约束了**按钮**的固有宽度，没有解决「文案独自承担全部压缩」这一根因。

### 变更

- `SignInHintBanner`：把图标与文案**先成组**，按钮不再与文案同行争宽；并用 `LayoutBuilder`
  实测单行是否放得下——放得下保持原有并排观感，放不下则让按钮整体落到第二行右对齐。
  文案因此至少能拿到整行宽度，不再被压成多行；按钮标签的 `maxLines: 1` + 省略号保留。

### 验证结论

- 新增 `test/core/widgets/sign_in_hint_banner_test.dart`（4 个用例：393dp/1.15 档单行断言、
  320dp/1.3 档无溢出、宽屏并排、按钮单行省略）。
- **该测试确为有效回归**：把 `page_state.dart` 临时还原到修复前，首条用例失败并报
  `Expected: <1> Actual: <2>`（文案确为 2 行）——即测试真的能抓住这个 bug，而非恒过。
- `flutter analyze` 全仓零问题；`flutter test test/{review,medicine,record,today,core}`
  全绿（含上述新用例）。

## fix(theme): 字阶并入紧凑基线，真机「大一圈」的第二层成因

### 背景

真机与模拟器的差异**不是渲染事故**，也不是模拟器测不出问题——两者跑的是同一套缩放逻辑，
只是真机才是与其他 App 同屏对比的场景。成因有两层：

1. **组件几何（已于 2026-10-12 修复）**：主题此前写死 Forui 的 touch 变体，组件整体大一级
   （field 36→44、item 30→44）。该次已切到 `touch: false`，但日志当时即注明「**未在真机复验**」。
2. **排版字阶（本次修复）**：`lib/core/theme/family.dart` 在 `touch: false` 的同时**显式**传入
   `FTypography.inherit(touch: true)`，即「组件紧凑、文字保持 touch 字号」。实测两个基线相差
   整一档，且**行高同时变大**：

   | 字阶 | desktop（应为） | touch（残留生效） |
   | --- | --- | --- |
   | `body.xs` | 12 / 1.0 | 14 / 1.25 |
   | `body.sm` | 14 / 1.25 | 16 / 1.5 |
   | `body.md` | 16 / 1.5 | 18 / 1.75 |
   | `body.lg` | 18 / 1.75 | 20 / 1.75 |

   行高增幅比字号更明显，这正是「字号看着大一圈、行距还松」的主因。对照 2026-10-12 日志
   「组件紧凑、文字保持可读」的原始取舍——该取舍与同一次改动自相矛盾（同一份主题里一半
   走 desktop、一半走 touch），按**漏改**处置。

### 变更

- `lib/core/theme/family.dart`：`FTypography.inherit(touch: true)` → `touch: false`，
  字阶与组件几何统一到 desktop 基线；文件头注释改记这一结论（含被推翻的旧理由）。
- `lib/core/design/tokens/markdown_style.dart`：`legal` 的正文 `body.sm` → `body.md`
  （长文固定 16px，否则切紧凑字阶后掉到 14px）；引用块同步 `sm` → `md`；标题阶梯保持
  h1=20 / h2=18 / h3=16（w600 区分）。
- `lib/app/bootstrap.dart` 的 `_applyHighContrast` **无需改动**：它原样透传 `theme.typography`，
  自动跟随新基线。

### 验证结论

- `flutter analyze` 全仓零问题。
- **`test/a11y/compact_text_scale_sweep_test.dart` 全 66 用例通过**——含此前一直失败的两个
  RecordPage 用例（360x800 / 320x720 @ 1.3）。即**上一节记录的 `date_bar.dart` 底线溢出
  随之消失**：Forui 的 `_estimateExtent()` 按 style 字号 × scale 计算条目高度，字阶降一档后
  条目自然落入 56dp 容器内，不需要再单独调 `_calendarItemHeight`。
- 全量 `flutter test` 通过。唯一的断言同步是 `test/core/design/markdown_style_test.dart`
  的 legal 正文用例（`sm`→`md`，期望值仍是 16px，并补充「标题高于正文」断言）。
- **未在真机复验**：与上次同样，最终观感需真机确认。

### 另行说明

应用**有意不跟随系统字号**：`lib/app/bootstrap.dart` 用自有的 4 档
（0.85 / 1.0 / 1.15 / 1.3，见 `core/accessibility/settings.dart`）覆盖 `textScaler`。
另外该处当 `accessibility` 尚未加载完成（`null`）时回落 `TextScaler.noScaling`，即首帧
不跟随系统字号——与真机观感无关，但属同一处的既有行为，记录备查。

### 附：`date_bar.dart` 溢出为何被本次改动一并消除

排查中途曾观察到 `flutter test test/a11y` 在 **RecordPage × {360x800, 320x720} @ 1.3**
两个用例失败：

```
A RenderFlex overflowed by 6.0 pixels on the bottom.
  Column: .../features/record/presentation/widgets/sections/date_bar.dart:107
  constraints: BoxConstraints(w=53.8, h=48.0)
```

当时先确认**与 `SignInHintBanner` 的改动无关**（临时还原 `page_state.dart` 后同样失败、
报错点相同；`git diff --stat lib/features/record/` 为空）。字阶并入紧凑基线后两个用例转为通过。

机理：`RecordDateBar` 用 `SizedBox(height: 56)` 包 `FLineCalendar`，但**该高度不决定条目高度**
——Forui 在 `calendar_layout.dart:_estimateExtent()` 里按 **style 字号 × scale + contentSpacing
+ 2×contentEdgeSpacing** 自行估算 extent，行高不参与。实测 style 字号为 `dateTextStyle=14`、
`weekdayTextStyle=8`，spacing=4、edge=13：

- touch 字阶 @1.3：`14×1.3 + 8×1.3 + 30 = 58.6`，而 `_CompactCalendarItem` 自身还有 8dp padding
  与 2dp spacing，条目远超 56dp 容器 → 底溢。
- 紧凑字阶 @1.3：字号降一档后估算值落入 56dp，溢出消失。

因此无需再单独调 `_calendarItemHeight`；`date_bar.dart:42` 那条注释所述「56dp 而非 48dp」的
历史修复方向本身是对的（要抬高容器），只是**真正的杠杆是字阶**，本次改动把它落到了实处。

## fix(theme): 全局收紧纵向密度——行高压到 1.0、间距上半档收紧、字重收敛为两档

### 背景

真机反馈「组件垂直高度太大、padding 太大留白太多」，且 token 使用不统一。先做了量化审计，
再对照成熟 App 的公开规范定规则。

审计结果：token 基建本身是干净的（裸 `fontSize:` 全仓 1 处、裸 `BorderRadius.circular` 0 处），
问题是**档位选择不统一**——字重四档混用（`w500` 7 / `w600` 94 / `w700` 147 / `w800` 56），
字号分布极度倾斜（`body.xs` 一档占 39%）。

### 变更

- **行高统一 1.0**（`lib/core/theme/family.dart` 新增 `_flattenLineHeight()`）：这是纵向空散的
  最大单一来源。Forui 各档自带行高，16px 的 `body.md` 占 **24px** 行框、18px 的 `body.lg` 占
  **31.5px**。压平后行框高度=字号（`md` 24→16、`sm` 17.5→14、`lg` 31.5→18），一张 10 行卡片
  直接矮约 80px。纵向节奏改由显式间距控制。
- **间距上半档收紧**（`lib/core/design/tokens/spacing.dart`）：`xl` 20→16、`xl2` 28→20、
  `xl3` 36→24、`xl4` 44→32。该 token 经核实**零处非间距用途**（全部是 `EdgeInsets` /
  `SizedBox` / gap），故改 token 值即可全局收敛，无需逐调用点改。下半档（`xs`~`lg`）与
  `xl5`+ 不动。
- **字重收敛为两档**（91 个文件、157 处）：`w500`/`w600`/`w800` 一并并入 `w700`，规则为
  **正文 `w400` / 强调 `w700`**。
- Markdown `ai` 样式的 `h6` 显式回到 `w400`：两档制下 h5/h6 同字号，靠字重收尾（否则 h5/h6
  完全无法区分）。

### 依据（对照四家公开规范）

| 来源 | 结论 |
| --- | --- |
| Material 3 | 15 档按 **5 类角色 × 3 尺寸**组织；`Title`/`Label` 用 **w500**、`Body` 用 w400 |
| Meta | 每档成对提供 Regular/**Bold**，字重只有 **400 / 700** 两档；卡片内边距 ≤24px |
| 微信适老化规范 | 标准版字号仅 **5 档**（22/17/14/12/10pt）；卡片内边距 16px |
| 美团 | 「**根据文字的位置确定样式**」——字号由角色决定；卡片内边距 16px、卡片间 8–12px |

### 关键判定：四档字重在真机上本就区分不出来

app **不内置 CJK 字体**：Forui 自带的 `Inter.ttf` 只含拉丁字形（`Inter` 无中文字形），
中文一律回落系统字体。而系统字体只暴露约两个真实字重面——Android（思源黑体/Roboto 回退）
通常是 Regular + Medium/Bold，iOS（PingFang SC）是 Regular/Medium/Semibold。
因此 `w600`/`w700`/`w800` 在真机上多为**合成加粗**，观感差异极小。

这解释了为何「同一类小块标题在不同文件里写不同字重」在代码里看不出问题、在真机上却显乱。
收敛为两档后，规则可执行且真机表现一致。

### 验证结论

- `flutter analyze` 全仓零问题。
- `test/a11y/compact_text_scale_sweep_test.dart` 全 66 用例通过（密度收紧未引入新溢出）。
- 全量 `flutter test` 通过。同步更新的断言仅两处：`spacing_tokens_test.dart`（档位新值）、
  `markdown_style_test.dart`（h5/h6 字重与两档制一致）。
- 自定义 lint `luminous_lints` 无新增告警（27 条 `layered_import` 为既有）。
- **未在真机复验**：最终观感仍需真机确认。

## chore(deps): 适配 flutter_local_notifications 22.x 的全命名参数 API

### 背景

依赖升级中 `flutter_local_notifications` 从 19.5.0 被拉到 `^22.3.1`（实际 resolve 到
**22.3.2**）、`timezone` 到 `^0.11.1`，编译期出现一批 error。

### 变更

按包内源码（`lib/src/flutter_local_notifications_plugin.dart`、
`platform_flutter_local_notifications.dart`）核对真实签名后逐点适配，未使用 `// ignore:`
或 `dynamic` 绕过。变更是 20.0.0 的 breaking change：`initialize()` / `show()` /
`periodicallyShow()` / `periodicallyShowWithDuration()` / **`cancel()`** / `zonedSchedule()`
的**位置参数全部改为命名参数**。

- `lib/core/notifications/local_notification_gateway.dart`：`initialize(settings:)`；
  `zonedSchedule(id:, title:, body:, scheduledDate:, notificationDetails:,
  androidScheduleMode:)`（两处，含 exact→inexact 回退分支）；`cancel(id:)`。
  注意 `cancel()` 也在这次破坏性变更内——它不在最初记录的清单里，靠编译错误发现。
- `lib/features/settings/domain/services/notification_permission.dart`：`initialize(settings:)`。
- `test/core/notifications/local_notification_gateway_test.dart`：
  `_FakeAndroidPlugin` / `_GatedAndroidPlugin` 的 `initialize` 与 `_FakeAndroidPlugin.zonedSchedule`
  override 改为同名命名参数签名。
- `test/settings/notification_permission_test.dart`：mocktail 的 `when`/`verify` 调用点由
  `initialize(any())` 改为 `initialize(settings: any(named: 'settings'))`。
- `test/helpers/mocks/scan.dart`：`FakeMobileScannerPlatform.getSupportedLenses` 跟上
  `mobile_scanner` 新增的 `{CameraFacing? facing}` 命名参数。

  并行写入范围，未触碰。
- `flutter test test/settings/notification_permission_test.dart test/core/notifications/`：
  全绿，**无需修改任何断言**（这是纯调用形态适配，通知语义、调度逻辑、权限流程均未变）。
- `timezone` 0.11.1 无需额外适配：`TZDateTime.from(DateTime, Location)` 与 `UTC` 位置导出的

## build(deps): 依赖全量升级并适配三组破坏性变更

### 背景

`Deploy Android` 连续失败，根因是 `sqlite3` 3.3.4 的 build hook 在下载 Android arm
ABI 预编译库时 **hash 校验失败**（该版本唯一变更恰是收紧了这一校验；期望值硬编码在包内
`asset_hashes.dart`，与 CDN 实际产物不一致）。同时 Dependabot 的 13 个 PR 全部 CI 失败，
其中 #19（37 个依赖更新）带三组破坏性 API 变更。

### 变更

- **依赖**（`pubspec.yaml`，与 PR #19 对齐）：`sqlite3` 3.3.4→**3.7.0**（显式声明，原为传递）、
  `sqlite3_flutter_libs` 0.5→**0.6.0+eol**、`drift` 2.34→**2.35**、`flutter_local_notifications`
  19→**22.3.2**、`timezone` 0.10→0.11、`forui` 0.26→**0.27.5**、`flow_ui` 0.1→**0.3.0**、
  `material_ui` 1.0→1.6、`flutter_riverpod`/`hooks_riverpod` 3.4、`riverpod_*` 4.0.9、
  `drift_dev` 2.35.1、`freezed` 4.0、其余 patch/minor 若干。
- **`flutter_local_notifications` 22.x**（54 个 error）：`initialize`/`zonedSchedule`/`cancel`
  从位置参数改为全命名参数（注意顶层是 `androidScheduleMode:`，fake override 层才是
  `scheduleMode:`）；测试 fake 的 override 签名同步；mobile_scanner 7.4.2 给
  `getSupportedLenses` 新增了可选命名参数。`timezone` 0.11 经核对无 API 变化，无需适配。
- **`flow_ui` 0.3.0**（9 个 error + 32 个测试失败）：
  - `FlowChatScreen` 更名 `FlowChatView`；`composer` 成为 required（只读处显式传 `null`）。
  - **assistant 文本默认按 markdown 渲染**：流式草稿因此丢失打字机动效——`buildMessage`
    对 streaming 轮次传 `markdown: false`，让其回到 `FlowStreamingText`；完成轮次不变。
  - **`FlowComposer` 需要 `material_ui` 的 `Material` 祖先**：0.3.0 的输入框是 material_ui 的
    `TextField`，而 `material_ui.MaterialApp` 不会在其 builder 之下插入一个——
    `withLuminousFlowTheme` 现以 `MaterialType.transparency` 包一层。
  - **链接确认弹窗须从 flow_ui 子树之外打开**：从 `FlowThread` 内部（material_ui Theme 之下）
    打开的 forui 弹窗，其按钮层收不到 tap。`_handleLinkTap` 改用
    `Navigator.of(context).context`（位于所有局部 Theme 之上）。
  - 测试适配：`page_test` 的 composer 查找改为 material_ui 类型（0.3.0 的
    TextField/InkWell 是 material_ui 的）；`scroll_behavior_test` 需越过按钮的
    **250 ms debounce**（0.3.0 起偏移须超过阈值持续该时长才解除 IgnorePointer）再 tap；
    FlowTheme 作用域测试删掉「无其它 Theme」的脆弱断言（material_ui 内部跨版本会插入）。

### 验证结论

- `flutter analyze` 全仓零问题。
- `test/a11y` 66/66、`test/assistant/` 226/226、全量 `flutter test` 全绿。
- 真机 Android 打包（sqlite3 hash 问题是否消除）待 CI 验证。
