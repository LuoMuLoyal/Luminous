# ADR-0008: 桌面端采用独立 Web 产品路线

- **Status**: accepted (amended 2026-09-27: 客户端代码归属由 Lucent 改为 Luminary；后端合同仍由 Lucent 提供；amended 2026-11-01: Flutter 桌面端恢复为在产平台目标，第 4/7 条被取代)
- **Date**: 2026-08-16
- **Deciders**: LuoMuLoyal
- **Related**: 产品文档 `docs/product/product-vision.md`、`product-mvp-scope.md`、`product-information-architecture.md`

## Context

Luminous 当前以 Flutter 手机客户端作为首发与用户价值验证表面。现有 Flutter Desktop 和桌面浏览器中的 Flutter Web 复用手机端的信息架构与功能，但桌面场景并不天然需要复制手机端的记录、提醒和五个入口；继续追求机械功能对等，会让手机端产品演进持续承担桌面布局、平台兼容和发布维护成本。

桌面端仍可能为个人用户提供手机屏幕不适合承载的阅读、比较和分析空间，因此本提案不永久放弃桌面产品，也不删除已经存在的 Flutter 桌面代码。需要决定的是桌面产品是否继续作为 Flutter 手机客户端的一个平台目标，还是成为具有独立产品边界的 Web 客户端。

### 2026-09-27 修订背景

原决定把独立桌面客户端的代码归属定在 **Lucent** 仓库。该归属经复核后不成立：

1. **技术栈不同构**。Lucent 是 NestJS 后端（ESM/SWC、Prisma、zod），其构建与门禁（`pnpm build` / `test:ci` / `export:openapi`）全部绑定后端语义。桌面客户端是 Next.js + React，放进去意味着同一仓库长期承担两套构建系统、两份 tsconfig、两种模块解析。
2. **改造成本与风险不对称**。Lucent 是线上服务所在仓库，为容纳前端而调整其 workspace 结构、构建脚本与 CI 边界，风险落在运行中的后端上，而收益仅是"代码同址"。
3. **存在同构宿主**。Luminary 已是 Next.js 16 + React 19 + TypeScript 的多产品聚合站，桌面客户端可直接复用构建链、React 版本与设计 token。

需要强调的是：**归属变更只涉及代码放哪，不改变"后端由 Lucent 提供"这一合同关系**。桌面客户端与手机端一样，是 Lucent API 的消费方，通过 OpenAPI 合同交互，不把后端实现搬进客户端仓库。

## Decision

采用以下产品与架构边界：

1. **桌面端走独立产品路线**：桌面产品拥有独立的信息架构、功能范围和发布节奏，不复制手机端五个入口，也不要求与手机端功能对等。（产品边界不变；「独立的 Web 客户端」这一实现载体已被 2026-11-01 修订取代，见第 9 条）
2. **独立桌面客户端使用 Next.js + Tauri**：工作台界面使用 Next.js，桌面发行包使用 Tauri；两者从工作台 MVP 起同步交付。**客户端代码归属 Luminary 仓库**（2026-09-27 修订，原为 Lucent），其仓库内目录结构由 Luminary 的 monorepo 计划规定。~~（已被 2026-11-01 修订取代，见第 11 条）~~
3. **后端服务由 Lucent 提供**：桌面客户端的认证、账号身份、健康数据、报告与通知等全部业务能力经 Lucent API 提供，不另建后端。Lucent 仓库只承载服务端实现与 OpenAPI 合同，不含桌面客户端代码。
4. **停止扩展现有 Flutter 桌面表面**：Flutter Desktop 和桌面浏览器形态的 Flutter Web 保留现有代码，不再新增桌面专属产品功能，不再以独立桌面产品对外发行；共享代码回归、安全修复和明确批准的维护任务除外。~~（已被 2026-11-01 修订取代，见第 9 条）~~
5. **手机端边界不变**：Android、iOS 以及面向手机浏览器的 Flutter Web 继续由 Luminous Flutter 客户端承担。桌面路线不得阻塞当前手机端发布与用户验证。
6. **共享业务合同，不共享页面结构**：手机端与独立桌面 Web 共享 Lucent 的 API 合同、账号身份、健康数据语义、授权与安全边界；各自维护适合自身任务的界面和交互。
7. **0.1.0 后启动桌面 MVP**：0.1.0 发布后直接启动工作台 MVP；具体 MVP 页面和功能集另行决策，不阻塞移动端发布。~~（已被 2026-11-01 修订取代，见第 9 条）~~
8. **桌面壳已选择 Tauri**：Tauri 与 Next.js 同步交付；PWA 或其他桌面分发方式不在当前路线内。~~（已被 2026-11-01 修订取代，见第 9 条）~~

### 2026-11-01 修订：Flutter 桌面端恢复为在产平台目标

原第 4 条「停止扩展现有 Flutter 桌面表面」与第 7 条「0.1.0 后启动独立的 Next.js + Tauri 桌面 MVP」被以下决定取代：

9. **Flutter Desktop 恢复为在产平台目标**：可新增桌面专属的产品功能、布局与交互，不再受「仅保留代码、只做维护」的限制。桌面端与手机端共享同一套设计语言与业务语义，差异体现在布局与密度，而非产品定义。
10. **手机端与桌面端同步演进**：任一端的改动在设计与实现时同时覆盖另一端，不做「先手机端、之后补桌面适配」的串行安排。桌面端不得阻塞手机端发布，手机端也不得把桌面端降级为事后适配。
11. **Luminary 内不再新建 Luminous 桌面客户端**：该仓库继续承担官网、文档站、个人站与 Lumine。Lumine 是独立产品（药品知识工作台），不承担 Luminous 桌面端的职责。

修订理由：

- **两套桌面客户端不成立**。原决定既保留 Flutter Desktop 的现有代码，又新建独立客户端，结果是同一批桌面用户被两个仓库、两套信息架构、两条发布链服务，产品事实有两个来源。
- **Flutter Desktop 已是可用资产**。桌面外壳与布局结构已经落地，丢弃重写等于把已付出的成本再付一次。
- **共享业务语义要求单一实现**。手机端与桌面端共享 Lucent 合同、认证会话与健康数据解释，差异只在布局与密度；双栈会把这种一致性退化成需要人工对齐的检查项。

第 3/5/6 条保持不变：Lucent 仍是 API 合同的唯一事实源，其仓库不含桌面客户端代码；手机端边界不变；手机端与桌面端共享业务合同、各自维护界面与交互。第 1 条的产品边界（桌面端拥有自己的信息架构与发布节奏）依然成立，只是承载它的不再是「独立 Web 客户端」。

## Options Considered

| Option | Advantages | Disadvantages |
|---|---|---|
| 继续用 Flutter 维护桌面与手机功能对等 | 最大化复用现有页面和 Dart 代码 | 桌面任务被手机信息架构限制；每次手机功能变化都带来桌面适配和回归成本 |
| **使用 Flutter 构建差异化桌面界面（2026-11-01 修订后采用）** | 保留单一客户端技术栈；可继续使用现有桌面基础设施；两端共享设计语言与业务语义 | 同一仓库需长期承担两套信息架构与平台条件分支 |
| 独立 Next.js Web 客户端 + Tauri 桌面壳，归属 Luminary 仓库（2026-09-27 至 2026-11-01 的选择，已放弃） | 产品边界清晰；可独立设计大屏交互；可同步提供浏览器与桌面发行形态 | 新增第二套客户端技术栈，以及与既有 Flutter 桌面代码并存的长期成本；同一批桌面用户被两个仓库、两套信息架构服务 |
| 同上，但归属 Lucent 仓库（2026-09-27 前的最初选择，已放弃） | 后端与客户端代码同址，合同变更时改动集中 | 同一后端仓库长期承担两套构建系统与模块解析；调整线上服务所在仓库的结构，风险不对称 |

## Consequences

- 手机端不再因未来桌面产品而承担机械功能对等要求；桌面端则以自身的任务边界演进，不复制手机五入口结构。
- （2026-11-01 修订）现有 Flutter 桌面代码恢复为在产资产，是新桌面方向的实现基础，不再是「停止产品扩展」的遗留物。
- （2026-11-01 修订）Luminary 不再承载 Luminous 桌面客户端；它继续承载官网、文档站、个人网站与 Lumine。任何客户端的实现都不得反向成为 API 事实源。
- Lucent 仍是 API 合同的唯一事实源，其仓库不含桌面客户端代码；合同变更需要可检测的跨客户端兼容检查。
- 两个客户端必须共同遵守 OpenAPI 合同、认证与会话规则、隐私授权、健康数据解释和安全边界。
- 桌面端需要单独解决大屏信息架构、窗口形态与可访问性；手机端需要保证自身的改动不依赖桌面端的适配节奏。这些属于后续设计与执行计划，不在本 ADR 中预先给出实现答案。
- 屏幕宽度跳转阈值、页面清单、MVP 阶段、发布时间和 Luminary 内目录结构仍需后续决定。
