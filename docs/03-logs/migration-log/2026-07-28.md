## 用药提醒编辑页 Bug 修复

### 频率选项点击无反应

- **文件**：`lib/features/medicine/presentation/widgets/reminder/form_fields.dart`、`lib/features/report/presentation/widgets/sections/ai_summary.dart`
- **根因**：`FSelectGroup` + `FMultiValueControl.lifted` 管理单选状态时，底层 `_ProxyNotifier.update()` 在点击新选项时将新值 **添加** 到集合中而不移除旧值，导致 `onChange` 回调收到 `{旧值, 新值}`。原代码 `value.first` / `selection.first` 按 Set 迭代顺序返回旧值，状态不变，UI 不刷新。
- **修复**：两处均改为 `value.where((v) => v != currentValue).firstOrNull` 过滤出新增的值。

### 开始/结束日期行间隙与边框消失

- **文件**：`lib/features/medicine/presentation/widgets/reminder/rows.dart`
- **根因**：`ValueActionRow` 使用 `FTile`，其 `FTileStyle.contentDecoration` 自带 `ShapeDecoration`（含 `color: colors.card` 背景和 `BorderSide` 边框）。这导致两个问题：
  1. 两个 `FTile` 用 `AppDivider` 分隔时，各自边框在分隔线上下产生多余间隙。
  2. `FTile` 的背景色会覆盖 `FCard` 的边框（`FCard` 的 `clipBehavior` 默认为 `Clip.none`，不裁剪子组件），导致边框消失。
  3. `FTile` 的 `borderRadius.md` 与 `FCard` 的 `borderRadius.lg` 不一致，底部圆角不统一。
- **修复**：完全弃用 `FTile`，改用 `FTappable` + `Padding` + `Row`（与 `SwitchRow` 等其他行一致的模式）。`FTappable` 不带 `ShapeDecoration`，不会覆盖 `FCard` 的边框和背景。`FCard` 的 `borderRadius.lg` 成为唯一的圆角边框来源，无论选择每日、每周还是自定义，底部都是统一的圆角。

## 通知列表页骨架屏不消失 + 无限重试 Bug 修复

- **文件**：`lib/features/notification/presentation/providers/notification.dart`
- **根因**：`NotificationListController.build()` 是项目中唯一未使用 `authGuarded` 的数据 provider。冷启动时 access token 已过期但 session 尚在 restoring，`build()` 直接发请求收到 401。`AuthInterceptor` 刷新 token 并重试成功（200），但 `handler.resolve()` 解决原始 401 错误后，Dio interceptor chain 对响应的处理存在微妙问题导致 `build()` Future 抛出异常。Riverpod 3.x 的内置重试机制（`ProviderContainer.defaultRetry`，指数退避 200ms→6400ms，最多 10 次）被触发，反复重建 provider 发送请求。约 38 秒后重试耗尽，`AsyncValue` 转为 `AsyncError`，UI 显示"加载失败"。
- **修复**：`build()` 方法改用 `authGuarded`，与 `notificationDetailProvider`、`notificationUnreadCountProvider` 及所有其他 data provider 保持一致。`authGuarded` 通过 `ref.watch(authSessionProvider)` 等待 session 恢复完成后才发请求，避免 token 过期时的 401 错误。session restoring 期间返回 `pendingAuthSessionResolution()`（永不完成的 Future），provider 保持 `loading` 状态。

## 同类 authGuarded 缺失修复

排查所有 `AsyncNotifier` 和 `FutureProvider`，发现 3 个 provider 同样在 `build()` 中直接调用 authenticated API 而未使用 `authGuarded`，存在冷启动 401→retry 循环的同类风险：

### `UserSettingsController`

- **文件**：`lib/features/settings/presentation/providers/user_settings.dart`
- **问题**：`build()` 直接调用 `repo.getSettings()`（`GET /api/v1/user/settings`），未等待 session 恢复。被 `SettingsAiPage` 和 `ReportPage` 直接 watch，冷启动时 token 过期会触发 401→retry 循环。
- **修复**：`build()` 改用 `authGuarded` + `pendingAuthSessionResolution` fallback。

### `DataExportController`

- **文件**：`lib/features/settings/presentation/providers/data_export.dart`
- **问题**：`build()` 直接调用 `_fetchLatest()`（`GET /api/v1/user/data-export-requests/latest`），被 `DataExportPage` 和 `ReportPage` watch。
- **修复**：`build()` 改用 `authGuarded` + `pendingAuthSessionResolution` fallback。`_fetchLatest` 本身不变，仍可被 `refresh()` 和 `requestExport()` 直接调用（这些是用户发起的操作，此时 session 已恢复）。

### `clinicSummaryPreviewProvider`

- **文件**：`lib/features/report/presentation/providers/clinic_summary.dart`
- **问题**：`FutureProvider.autoDispose` 直接调用 `POST /api/v1/user/reports/clinic-summary/preview`，无 session 检查。
- **修复**：改为使用 `authGuarded` + `pendingAuthSessionResolution` fallback。
